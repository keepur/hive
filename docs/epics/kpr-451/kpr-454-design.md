# KPR-454 — Runtime tool-failure producer: the first `ops_events` publisher

## TL;DR

KPR-454 makes the engine state, as a durable published fact, that a tool failed — on both provider lanes, from one capture point each, in the vocabulary KPR-458 fixed. It is the **first producer** conforming to that contract: it owns the accept path (validate → resolve epoch → match → one immutable insert), the `ops_events`, `ops_subscriptions` and `ops_reasons` collections and their boot-order wiring, its own reason-registry rows, and nothing else. It delivers nothing, notifies nobody, and holds no ledger — those are KPR-468's. Shipped alone it is *staged, not broken*: every tool failure is recorded with a truthfully stamped `matchedSubscriptions: 0` and the log is queryable while no notification exists. The ticket body is stale on its two central mechanisms and both are superseded here with reasons: the `agent_events` + `deliveries: []` store-only trick is the mechanism KPR-458 D10 rejects, and `PostToolUse` is the SDK's **success** hook — the failure hook is `PostToolUseFailure`, which this repo's own shipped CLI documents in one line.

## Key Points

- **Two capture points, and the ticket named the right lines for the wrong halves.** The Claude lane needs **both** SDK hooks: `PostToolUseFailure` (typed `tool_name` / `tool_input` / `error` / `is_interrupt` / `duration_ms`) is the failure signal, and `PostToolUse` — which the shipped CLI's own hook table describes as *"Run after successful tool"* — is the **recovery** signal D2 makes an obligation. Lane B needs both halves at one site: `wrap()`'s `catch` (`tool-bridge.ts:352-356`) and the success block immediately above it (`:349-351`). Every Lane B failure — MCP `isError` converted to a throw in `discover()`, a builtin throw, a transport rejection, a delegate `Task` fault — passes through that one `catch`.
- **The condition is the tool, not the work item.** `subject: { kind: "tool", id: "<canonical tool name>" }`. Keying on `workItemId` would mint a fresh condition per turn and reproduce exactly the flood this epic exists to remove; keying on the tool collapses a flapping tool into one renewing condition, which is also what D8's tool-health view already assumes (it keys on `detail.tool` / `detail.errorSig`, i.e. from `detail`, not from `subject`). `workItemId`, `threadId` and `agentId` ride `detail`; `workItemId` also rides `evidence` when present.
- **`workItemId` is optional and this producer must survive its absence.** KPR-453 canon: detached worker and scribe executions carry no `WorkItem`. Those are precisely the turns nobody is watching, so a design that drops their failures drops the most valuable rows. Because the subject is the tool, they publish normally; the absent id is simply an omitted `detail` key and a `waiting: nobody`. **That same absent shape now also absorbs an id the runtime cannot vouch for** — the ws/app channel accepts a client-supplied WorkItem `id`/`threadId` behind a bare `typeof === "string"`, and a `sched:` id embeds the operator's free-form cron task label, so D6 bounds those three stored values to an admissibility token and **omits** rather than rejects on breach, keeping C13 true by construction without letting a client drive the rejection counter.
- **`errorSig` is an enumerated token, never a hashed or truncated message.** D9's words are "tool name plus an enumerated error token". One exported pure classifier, one closed nine-value set, typed signals first and a small fixed token test after, defaulting **to `unclassified`** — which is what keeps C13 true by construction rather than by a scrub pass. `invocation` from the ticket body is dropped: tool arguments are named in C13's prohibited list.
- **Own-abort is not a tool failure; a foreign interrupt is.** Both lanes suppress the publish when the turn's own abort is already set (`AgentRunner.wasAborted`; `opts.signal.aborted`) — a deadline kill is not a tool fault. An interrupt the runtime did **not** cause still publishes, as `errorSig: "interrupted"`, which makes this producer the standing detector for the KPR-438 background-subagent signature.
- **A fourth collection is forced, and this is the child that must define it.** D4 requires the reason registry to be *data* so an out-of-engine producer can add rows without an engine change, and D11 column 3 gives the operator `enabled` as a lever — neither has a home in D1's three collections. KPR-454 defines `ops_reasons`, upserted at boot from the producer's code-resident rows, **never overwriting operator-set `enabled`**. That toggle is also this ticket's whole kill switch: `enabled: false` + restart stops publication, because C5 fails an unknown-or-disabled `(producer, reasonId)` closed. No new hive.yaml key ships.
- **Publishing is off the turn's await path, but not fire-and-forget.** A bounded in-process queue with a single drainer (KPR-456's `inFlight` + drain-before-shutdown precedent) keeps the turn free of the two indexed reads D2's epoch resolver needs, bounds concurrency under a failure storm, serializes the open-condition map, and gives shutdown something to drain. Overflow drops oldest and counts. A publish fault is warned and counted — **never published** (D10 invariant (a)).
- **Lane B needs one stable-identity fix, and it is small.** `ToolBridgeOptions.agentId` is documented "logging/telemetry label only" and is fed `config.name` — the **display name**, which D5 says is never an identity. `ProviderTurnAssembly` gains an optional `agentId?: string` (the `agent_definitions` slug), the KPR-432/434 additive-optional pattern for a frozen provider ABI; absent ⇒ the `agentId` detail key is omitted, never guessed.
- **No new MCP server, no agent-facing publish tool, no containment change.** The two KPR-390 standing obligations (Lane B inventory compensation, the three `suppressAutoInjectedServers` gates) are inapplicable because no server is added, and `WORKER_SERVER_DENYLIST` is untouched. Contained workers do publish — the runtime publishes *about* them, with allow-listed fields only; a worker cannot choose to, so no outbound surface opens.
- **In scope:** the two capture points, the error-token classifier, **a ⚠ refactor of the existing production file `src/outage/outage-notices.ts`** — the live outage-notice path `dispatcher.ts:872`/`:1103` calls — collapsing its five-arm prefix chain into one shared prefix table behind a single `sourceOfId` predicate, from which both `policyForId` and the new `waitingFor` project as exhaustive `Record` maps (D7; the only edit in this ticket that touches shared production code outside the new ops machinery, behaviour-preserving and pinned per prefix by test), the accept path including match evaluation and the `matchedSubscriptionIds` stamp, the open-condition map and the recovery publish, the three collections' shapes/indexes/boot wiring, this producer's reason rows, `CLAUDE.md` entries. **Out of scope:** ledger, delivery, transport adapters, nudging, snooze, clearing *application*, acknowledgement intake (all KPR-468); the inbound acknowledgement edge and every reader (KPR-455); every row of D11's third column; widening `system:task_blocked`; any `hive doctor` section; any dashboard.

## Two supersessions of the ticket body

The ticket body predates the contract and is stale on both of its central mechanisms. Neither is a judgement call.

**1. `agent_events` with `deliveries: []` is the rejected mechanism, not a variant of it.** The body proposes `system:tool_failed {…}` "written with `deliveries: []` (store-only; `hasPending: false` so the scheduler never dispatches it)". That is the same collection whose publish-time fan-out spawns turns, configured not to fan out. KPR-458 D10 declines it in terms: the fan-out "*dispatches agent turns*", and an operational-failure feed sharing a collection with a turn-spawning bus "is one field away from a spend loop". Verified at this tree: `Scheduler.checkEvents` (`src/scheduler/scheduler.ts:322-413`) iterates `{ hasPending: true }`, atomically flips each pending delivery to `fired`, and calls `agentManager.runWorkItemTurn(delivery.agentId, workItem)` at `:402`. `EVENT_SCHEMAS` (`src/events/event-types.ts:15-134`) is a closed **13-type** zod map over five domains whose `system:task_blocked` payload is `{taskId, description, blockedBy}` — it cannot carry D2's envelope. KPR-454 therefore writes `ops_events`, and the coordination bus is untouched, including the `subscribe: string[]` agent-definition field, which stays the event-bus domain list and is never overloaded to mean an ops subscription.

**2. `PostToolUse` is the success hook.** The shipped CLI binary at this tree (`@anthropic-ai/claude-agent-sdk@0.3.258`, platform dep `claude-agent-sdk-darwin-arm64`) carries its own hook-event table, verbatim: `| PostToolUse | Tool name | Run after successful tool |` and `| PostToolUseFailure | Tool name | Run after tool fails |`. `PostToolUseFailureHookInput` (`sdk.d.ts:2446-2457`) is `BaseHookInput & { hook_event_name, tool_name, tool_input, tool_use_id, error: string, is_interrupt?, duration_ms? }`; `PostToolUseHookInput` (`:2464-2475`) carries `tool_response` and no `error`. A PostToolUse-only implementation would attach to the success path and publish nothing. Both events are in `HOOK_EVENTS` and in the `HookEvent` union, so both are wireable through the existing `Partial<Record<HookEvent, HookCallbackMatcher[]>>` shape with no type work. The body's two insertion points are otherwise correct and are used, re-assigned: `PostToolUseFailure` carries the failure, `PostToolUse` carries the recovery D2 requires.

**What carries forward unchanged from the body:** the two lanes' insertion points, and "redaction is a zod field allow-list on the event schema at write time — not scrub-after". That rule is now KPR-458 C13/D9 rather than a fresh idea, and D4's `detailKeys` is its mechanism.

## Goals and non-goals

**Goals.** State a tool failure as a published fact on both lanes, from one capture point per lane, in the D2 envelope. Publish the recovery that makes D2's epoch rule work. Make the fact honest with no subscriber, no ledger and no transport in existence. Never fail, delay, or alter a turn. Store no message text, no arguments, no raw error.

**Non-goals.** Any ledger row, delivery, adapter, nudge, snooze, clearing application or acknowledgement intake (KPR-468). Any reader, view, dashboard, `hive doctor` section or inbound acknowledgement edge (KPR-455). Any subscription row, transport binding, cadence value, nudge floor, staleness horizon or retention *value* (D11 column 3, operator). Any agent-facing publish tool. Any change to `agent_events`, the scheduler, `activity_log`, delivery routing, or KPR-456's obligation path. Any new hive.yaml key. Turn-deadline, provider-outage or obligation events — other producers, other tickets.

## Design

### D1. Producer identity, and the three collections this child owns

`producer: "hive-runtime"` — the engine itself, reporting what it observed. It is a bounded lowercase-hyphen token per D2, not an enum member, and adding a second producer later is rows.

KPR-454 creates, indexes, documents and wires:

- **`ops_events`** — D1's append-only log. Nothing in it is ever mutated. One document per publish.
- **`ops_subscriptions`** — D5's subscription documents. This child **creates the collection, its index, and the in-memory loaded set**, and registers **zero rows** (D11 column 3). It reads them; the operator writes them.
- **`ops_reasons`** — the D4 reason registry, defined here because D1 named three collections and D4 needs a fourth. See D5.

`ops_notifications` is **not** created here; it is KPR-468's, per D12's boot-order split.

All four get `CLAUDE.md` MongoDB-collections entries in this ticket's diff except `ops_notifications` — the KPR-452 precedent that a collection documented only in a spec is invisible to the next reader.

### D2. The Claude lane: two hooks, one job each

`buildHooks(context)` (`agent-runner.ts:1936`) gains two matchers beside `PreCompact`. Both are unmatched (all tools), both are `async`, both **return an empty object** — they never rewrite output, never set `additionalContext`, never block. The SDK's `PostToolUseHookSpecificOutput` offers `classifierContext` and an output rewrite; neither is used, and a test pins that the returned object is empty, because a hook that alters tool output would breach C15's "cannot alter a turn's outcome" on the one path where altering is trivially available.

```
PostToolUseFailure  →  observeToolFailure({ tool: input.tool_name, error: input.error,
                                            isInterrupt: input.is_interrupt,
                                            durationMs: input.duration_ms, lane: "claude" })
PostToolUse         →  observeToolSuccess({ tool: input.tool_name, lane: "claude" })
```

Three rules bind the wiring:

1. **Own-abort suppresses.** Both callbacks read `this.wasAborted` at fire time and return immediately when set. A turn killed by its wall-clock deadline (KPR-402) or by an operator abort produces tool errors that are consequences of the kill, not faults of the tool. `is_interrupt` alone does **not** suppress: an interrupt the runtime did not cause is a real fault, and it is the KPR-438 background-subagent signature (`"The tool call was interrupted before a result was received"`, in-process MCP only) that this producer should be the standing detector for.
2. **Identity is read at fire time, never captured at build time.** The callbacks read `this.workItemContextRef.current` (KPR-453's live reference) and `this.agentConfig.id` (the stable slug). `buildHooks` is rebuilt per `send()` and `AgentRunner` is per-spawn, so capture-at-build would be equivalent today — reading `.current` is required anyway, because KPR-453 canon fixes the pattern rather than the coincidence, and a future runner reuse must not silently mis-attribute. Absence is honest: a missing `workItemId` omits the detail key.
3. **The archetype `PreToolUse` fail-closed arm is untouched.** Its `catch` installs a deny-all matcher; these two matchers are added outside that `try` so a broken archetype cannot disarm failure observation, and a broken observer cannot disarm archetype policy.

Subagent-originated failures are included: `BaseHookInput.agent_id` is present only inside a subagent, and no filtering is applied — a delegate's tool failure is a runtime tool failure. `agent_id` is **not** stored; the publishing agent is the parent's stable slug, matching Lane B, where a nested delegate turn's bridge carries the parent's assembly.

### D3. Lane B: one site, two lines

In `wrap()` (`tool-bridge.ts:318-359`), unchanged in structure:

- **Success** — beside the existing `this.record(name, Date.now() - t0)` at `:350`, add `observeToolSuccess({ tool: name, lane: "laneB", … })`.
- **Failure** — beside `this.record(...)` at `:353`, before the containment return at `:355`, add `observeToolFailure({ tool: name, error: errorText(err), … })`.

Four things are deliberately **not** published from this method:

| Site | Text | Why not |
| --- | --- | --- |
| `:341-342` | `Tool call denied by policy: …` | A guardrail deny is policy working, not a fault. Publishing it would make correct enforcement look like breakage. |
| `:344-345` | `Tool execution aborted (…)` | Pre-execution abort check; the turn is already dying. |
| catch, when `this.opts.signal.aborted` | — | Abort **during** execution surfaces as a rejection and would otherwise be indistinguishable from a fault. Reading the signal in the catch is Lane B's exact analogue of the Claude lane's `wasAborted`, and the two lanes must suppress the same class or the tool-health view is lane-skewed. |
| `discover()`'s `isError` conversion | — | Not a separate site: it throws precisely so this one catch handles it (`:290-308`). Nothing is added there. |

The name published is `name` — the argument `wrap()` closed over, i.e. the canonical `mcp__<server>__<tool>` or builtin name **before** `applyNameAndCapEdges` sanitizes/truncates/de-collides for provider constraints (`:446-…`). That method builds a new object and never rewrites the closure, so the canonical name is what reaches the publisher, and Lane A/Lane B/Claude rows for one tool share a `subject.id`. A test pins this against a name long enough to trigger truncation.

### D4. Subject, dedupe key, and the identity of the condition

```
subject = { kind: "tool", id: <canonical tool name> }
dedupeKey = "hive-runtime:tool:<toolName>:tool-failed:<generation>"      (D2's formula, unchanged)
```

**Bounds, because D2 requires `subject` bounded and only `detail` gets them for free.** `detail.tool` is bounded by its `detailKeys` declaration like every other detail key, so it needs nothing here. `subject.id` is *not* covered by that mechanism and so carries its own explicit bound: **`subject.kind` matches `^[a-z][a-z0-9-]{0,39}$` and `subject.id` is 1–200 characters**, validated at accept, over-length **rejected and counted** (C5) rather than truncated — truncation would silently merge two tools into one condition, which is the one failure this subject choice exists to avoid. 200 is generous against the real population: the longest names here are `mcp__<server>__<tool>`, and the Lane B provider caps that `applyNameAndCapEdges` exists to satisfy are far tighter, so a rejection is a bug signal rather than an expected event.

**Why not `subject.kind: "workItem"`.** KPR-453 canon says an item id "proves neither unique attempt nor task continuity", and D2 spells out that a workItem subject collapses one turn's retries into one condition. That is the right granularity for a *turn* fact; it is the wrong one for a *tool* fact. A tool broken for a day fails across hundreds of work items, minting hundreds of conditions and — once KPR-468 exists — hundreds of ledger rows and hundreds of first deliveries. That is the flood the epic exists to remove. Keying on the tool makes it one condition that renews (D7 rule 4: `latestEventId`, `lastEventAt`, `eventCount` advance and nothing new is sent), and it matches D8's tool-health view, which keys on `detail.tool` / `detail.errorSig` and therefore already assumes the signature lives in `detail` rather than in `subject`.

**The accepted cost, stated rather than buried.** All error tokens for one tool share one condition, and all agents share it. A tool that times out for agent A and rejects agent B's input is one row, whose `detail` shows the *latest* event's token. Remediation is per tool, so this is usually right; when it is not, the recorded evidence is still complete in the log, which is where D8's view reads. ⚠ Non-blocking, listed in Assumptions: the alternative (`subject.id = "<tool>#<token>"`) is a one-line change bounded by the nine-token set.

### D5. The reason registry: rows this producer ships, and where they live

**Two rows, both `producer: "hive-runtime"`, both shipped with this code and enabled at its deploy** (D11 column 2):

| `reasonId` | `class` | `retry` | `clearsReasonIds` | `detailKeys` | `remediationTemplate` |
| --- | --- | --- | --- | --- | --- |
| `tool-failed` | `resource` | `transient` | — | `tool`, `errorSig`, `agentId?`, `lane`, `threadId?`, `workItemId?`, `durationMs?` | `"retry {tool}; if it repeats, inspect its {errorSig} failures on lane {lane}"` |
| `tool-recovered` | `informational` | `transient` | `["tool-failed"]` | `tool`, `lane` | `"none; recorded so {tool} reopens as a new epoch if it returns"` |

This is the shape D2 and D4 require and mirrors KPR-458's own example table: an operational fault is `resource`, its clearing fact carries its **own** registered reason so it never notifies the condition's subscribers, and `informational` means no subscription selects it unless someone deliberately asks for recoveries. `retry: transient` is the honest default for a mixed population — a tool that failed once may succeed on the same input — and D3's stated lever for a genuinely deterministic class is a *second reasonId*, not a per-event assertion. ⚠ Delegated, non-blocking.

**The remediation template interpolates only always-present keys, which is why `{agentId}` is not in it.** `agentId` is optional and is absent on exactly the detached worker and scribe rows this spec calls its most valuable case (Key Points; D7's `waiting: nobody` derivation), so a template naming it would render a hole on the best rows and would force KPR-468 — which renders these at delivery (C13) — to invent an optional-parameter rendering rule this ticket has no reason to specify. `{tool}`, `{errorSig}` and `{lane}` are declared, always present and bounded; the agent is recoverable from `detail` by any reader that wants it, and remediation for a failing tool is per tool rather than per agent (D4).

**`ops_reasons`, and why a fourth collection is forced.** D4 says "Adding a reason is a row… Neither is an engine change — which is what lets Florist come online later with producers that do not exist today", and D11 column 3 gives the operator `enabled` on an individual reason. Neither is expressible if the registry is a code constant, and D1 named no collection for it. KPR-454, as the first producer, defines:

```
ops_reasons: { _id: "<producer>:<reasonId>", producer, reasonId, class, retry,
               remediationTemplate, detailKeys[], clearsReasonIds?, enabled }
```

with a unique index on `(producer, reasonId)`. At boot the producer **upserts its own rows** from the code-resident table, writing every field **except `enabled`**, which is `$setOnInsert: true` — so an operator who disabled a reason keeps it disabled across upgrades, and a code change to a template or an allow-list still lands. D4's enable gate is enforced over that table: a `class: resource` row may not be left enabled unless some registered row lists its `reasonId` in `clearsReasonIds`. Both rows ship together, so the gate passes; it is still implemented, and it refuses loudly rather than silently publishing an unclearable condition. **The gate is a pure precondition over the code-resident table, evaluated before any I/O and pinned by a unit test** — so a violation is a development-time throw, never an operational boot fault, and it is therefore untouched by D10's rule that `init()`'s I/O is non-fatal to boot.

**But the gate is a precondition over *code*, and the upsert is two writes over *data* — so the write order is load-bearing: `tool-recovered` is upserted FIRST, `tool-failed` second.** Both rows are registered as one code-resident set, which satisfies **both** of D4's clauses: the enable gate (`tool-recovered` lists `tool-failed` in `clearsReasonIds`) and the separate registration clause, "a row naming an unregistered reason is rejected at registration". The write order decides only *which* illegal intermediate state a fault between the two writes can leave persisted, and **neither order leaves every prefix of the write sequence legal** — the round-2 justification that claimed otherwise was reasoning from the enable gate alone and missed D4's registration clause, which clearing-first violates. So the choice is a severity comparison between two illegal middle states, and it is not close:

- **Failure-first** leaves a persisted, **enabled**, `class: resource` `tool-failed` row that no registered reason clears — exactly the state D4's enable gate exists to refuse and C19 tests at registration. It is live and consequential: it survives into every later reader (KPR-455), and once KPR-468 exists a condition raised under it could never be cleared, which is D2's permanent silence.
- **Clearing-first** leaves a persisted `tool-recovered` row whose `clearsReasonIds` names a reason that is not yet registered — illegal under the registration clause, and inert in every direction that matters. `tool-recovered` is `informational`, so nothing selects it; its `clearsReasonIds` is read only by the enable gate and by C19's publish-time check, and with `tool-failed` unregistered, C5 fails closed on every `tool-failed` publish, so no event carrying a `clears` key into that family can exist to be checked against it. A dangling forward reference that nothing dereferences is a bookkeeping defect; an enabled unclearable `resource` reason is a silence generator.

**A third write shape would leave every prefix legal, and is still not taken.** Upserting `tool-failed` **disabled**, then `tool-recovered`, then enabling `tool-failed` makes every intermediate state legal under both of D4's clauses at once, so the severity comparison above would not have to be made. It is declined on cost rather than on correctness: a blind phase-3 `$set: { enabled: true }` would re-enable a row an operator had deliberately disabled, on every boot, destroying the kill switch this section rests on — so the enable would have to be made conditional on the phase-1 upsert's own result, which is strictly more code and one more round trip, spent to remove an inert forward reference that the next boot already repairs.

Self-heal applies identically to both, which is what bounds the residual to a single boot: a registry-upsert fault leaves the publisher **unset** (D10), so nothing publishes on that boot under either order, and the next boot re-runs both upserts unconditionally and repairs whichever partial state it finds. The round-2 review's alternative — after a partial failure, re-run the D4 gate against what is actually persisted in Mongo and unset or disable the illegal row — is declined: it is strictly more I/O and more code to repair, one boot early, a state the ordering has already reduced to an inert forward reference no code path reads.

**`enabled: false` is this ticket's entire kill switch.** C5 fails an unknown *or disabled* `(producer, reasonId)` closed, so flipping `tool-failed` to `enabled: false` and restarting stops publication with no code change and no config key — which is why no hive.yaml lever ships (the standing "no preemptive levers" preference, and KPR-458's own posture of shipping no policy).

### D6. The `detail` allow-list, the `evidence` references, the error-token taxonomy, and the stable-id fix

**Redaction is the schema.** `detail` is validated by a zod object built **from the registry row's `detailKeys`** — not a hand-written second schema, or the two drift. Unknown key, wrong scalar type, over-length value or non-scalar ⇒ the publish is **rejected and counted** (C5). Nothing else is stored: no `tool_input`, no `tool_response`, no raw `Error`, no stack, no URL, no path, no prose. The ticket body's `invocation` field is therefore dropped — tool arguments are named verbatim in C13's prohibited list, and a diagnostics surface is exactly where a token gets written.

**Three of the stored values do not originate in the engine, and a length bound alone does not make C13 true for them.** `detail.workItemId`, `detail.threadId` and `evidence[].id` (the same work-item id) are the only fields here whose *content* is authored outside this producer, and two independent paths put untrusted text into them. Verified at this tree: `ws-adapter.ts:262` builds the WorkItem as `id: msg.id || randomUUID()` and `:563` as `threadId: msg.threadId ?? "team:<channelId>"`, while the validator's treatment of both is nothing but a bare `typeof === "string"` — `ws/protocol.ts:228` for `msg.id`, `:235` for `msg.threadId` — with no length and no format check, so an app client supplies them verbatim. And `scheduler.ts:231`/`:236` embed the **operator-authored cron task label** in `sched:<agentId>:<task>:<epoch>`, which is free-form and routinely multi-word. So C13's "no free-form prose in any stored field" is not guaranteed by construction for these three keys, and the round-4 review is right that a length bound is the only thing standing there today.

**The rule is an admissibility token bound, `^[A-Za-z0-9_.:#+-]{1,200}$`, checked at the capture point — and a value that fails it is *omitted*, not rejected.** The charset is sized to the machine-generated id population read at this tree, all of which passes: Slack's `1725465600.123456` and `slack:<channel>:<ts>`, `imsg-<rowId>`, `callback:<oid>`, `event:<id>:<agent>:<epoch>`, `team-<oid>`, `worker:<claimId>`, `sms:<line>:+1555…`, KPR-402's `<baseId>#dl1`, and `randomUUID()`. The length reuses `subject.id`'s 200 rather than inventing a second number.

Omit-rather-than-reject is the load-bearing half of that rule, and it is chosen on three grounds rather than convenience. **It keeps the fact.** The event is a tool failure; the id is one optional attribute of it, so rejecting the publish would trade a real failure record for a bad decoration — the exact inversion of this producer's purpose. **It keeps the rejection counter meaningful.** D9 reserves that counter as the signal of a *mis-integrated producer*; a malformed client id says nothing about the producer, and letting any app client increment it at will would convert an integrity signal into client-controlled noise. **And it lands in a state that already exists.** `workItemId` is optional by KPR-453 contract, and an absent one already yields `waiting: nobody` and `evidence: []` — the detached worker and scribe case — so an inadmissible id produces a row this spec already specifies and every reader already handles, rather than a new shape.

The check therefore lives at the capture point, before the observe call composes `detail`, and **not** in the accept-path validator, so the two mechanisms stay separate and each stays honest: the capture point *omits* an id it does not trust, and the accept path still *rejects and counts* any producer-supplied `detail` value that breaches its declared bound (C5), never truncating. Omissions are counted separately, as `idOmitted`. The deliberate consequence is that a multi-word cron task label makes its `sched:` id inadmissible, so scheduled-turn rows carry no `workItemId` or `threadId` and an empty `evidence` — which is the *right* answer and not a loss, because such an id is precisely the operator prose C13 prohibits; the row keeps `tool`, `errorSig`, `lane` and `agentId`, which is what remediation reads (D4). The asymmetry with `subject.id`, which keeps reject-and-count and gets no charset bound, is also deliberate: a tool name comes from engine and plugin space rather than from a channel client, a breach there really is the mis-integration the counter is for, and a subject is *required* — there is no omit branch available for it, which is why D4 argues truncation-versus-rejection there and this paragraph argues omission-versus-rejection here. ⚠ Delegated, non-blocking: the exact charset.

**`evidence`: this producer's `kind` vocabulary, and why a recovery carries none.** D2 defines `evidence` as a bounded array of `{kind, id}` references — "an activity row, a work item, a thread, a receipt" — and, exactly as with `subject.kind`, supplies no closed enum: the vocabulary names the producer's own key space. KPR-454 is the first producer, so it defines its own, and states it here rather than leaving AC1's key-set test to pin a field whose contents nothing specifies.

- **`tool-failed`** writes `evidence: [{ kind: "workItem", id: <workItemId> }]` when `workItemId` is present **and admissible under the token bound above**, and `evidence: []` when it is not — the detached worker and scribe case (D2/KPR-453) and the inadmissible-id case, which deliberately land in the same shape. That single token, `workItem`, naming the KPR-453 work-item id, is this producer's entire `kind` vocabulary. `threadId` is deliberately **not** mirrored here: it is a filterable attribute of the condition and belongs in `detail`, whereas `evidence` points at the record a responder would open next.
- **`tool-recovered`** writes `evidence: []`, always. The turn that happened to succeed is an arbitrary later turn — the same reasoning that fixes the recovery's `waiting` to `nobody` in D8 — so attaching *its* work item would point a reader at a stranger's record as though it were part of the condition. The recovery's link to what it closes is `clears`/`clearsFamily`, which is a stronger and already-indexed reference than any evidence row could be. **The same objection retires `agentId` from `tool-recovered`'s `detailKeys` (D5), and that is the third and last place it applies.** The only agent slug reachable on the recovery path is the one running that same arbitrary later turn, so storing it attributes a stranger's agent to the condition exactly as its work item and its waiter would have; three refusals of one attribution are resolved the same way rather than two ways and a leak. `lane` survives the objection and stays declared, because it names the *capture point* that observed the success — a property of the observation, attributed to nobody. A reader who wants to know which agent was running when a tool came back reads the `tool-failed` rows, where the agent is recorded and means something.
- **Empty is written, never omitted.** `evidence` is always present, `[]` when there is nothing to reference, so AC1's key-set assertion stays unconditional and `clears`/`clearsFamily` remain the only genuinely conditional pair. This also removes the absent-versus-empty question outright, which matters because D2 binds readers to infer nothing from absence.
- **Bounds, validated at accept like everything else (C5):** at most 4 references; `kind` matches the same `^[a-z][a-z0-9-]{0,39}$` token bound as `subject.kind`; `id` is 1–200 characters, matching `subject.id`. Over-bound ⇒ rejected and counted, never truncated. This producer never emits more than one reference, so the array bound is a schema guard for a future producer sharing the accept path rather than a live constraint here.

**The error token — one closed set, one exported pure classifier**, `classifyToolError(...)` in a single module used by **both** lanes (the C6 / KPR-452-D1 one-predicate discipline; a second classifier drifts):

`timeout` · `interrupted` · `transport-unavailable` · `not-found` · `invalid-input` · `permission-denied` · `rate-limited` · `upstream-error` · `unclassified`

**The token is stored under the detail key `errorSig`.** D8 fixes the tool-health view as keyed `(detail.tool, detail.errorSig)`, so the *field name* is contract rather than producer choice, while D9's phrase "an enumerated error token" names the *value*. This spec therefore says "error token" for the value and `errorSig` for the field throughout; the classifier is `classifyToolError` and its return type is the token union. There is no `errorToken` key on any stored document.

**`lane` names the capture point, not the provider.** Its two values are `claude` and `laneB` — which capture site observed the failure, the SDK hook pair or `wrap()`. Lane A (kimi/deepseek) runs the full Claude runtime, so a Lane A tool failure is captured by the hooks and stamped `lane: "claude"`, which is correct and must not be read as "the turn ran on Anthropic". A reader who wants the provider must join through `agentId` to the agent definition's `model`; this producer deliberately stores no provider field, because the provider is not a property of the tool condition and D8's view key is `(detail.tool, detail.errorSig)`.

Classification reads **typed signals first** — an MCP error class, an HTTP status where one is carried, the SDK's `is_interrupt`, the bridge's own `TOOL_CALL_TIMEOUT_MS` path — and only then a small fixed set of case-insensitive substring tests over the error text, which is used **for classification and then discarded**. Anything unrecognised is `unclassified`. Two properties are load-bearing and both get tests: the classifier is total (every input returns a token) and its output is drawn only from the closed set, so no message fragment can ever reach a stored field. A test feeds it a credential-shaped and a path-shaped error and asserts the token, and asserts that no substring of the input appears in the published document.

**The stable-identity fix.** `ProviderTurnAssembly` gains `agentId?: string` — the `agent_definitions` slug — set by `assembleProviderTurn`, carried into `ToolBridgeOptions` by the scaffold (`turn-scaffold.ts:186-196`) as a new non-ABI field. Optional because the type is frozen provider ABI at `LANE_B_PROVIDER_ABI_VERSION = 1`; this is exactly the `datetimeInTurnInput?` / `memoryInTurnInput?` precedent and needs no version bump. Absent ⇒ the `agentId` detail key is omitted (it is optional in `detailKeys`), never substituted with the display name, never guessed. `ToolBridgeOptions.agentId` keeps its documented meaning and its existing log call sites; nothing renames it. Nested delegate assemblies carry the parent's slug, matching the Claude lane's treatment of subagents in D2.

### D7. `waiting`, derived once, from the one prefix table

C6 requires `waiting` to come from a function co-located with `policyFor` sharing its prefix table, with no second prefix predicate in the repository. `policyFor` takes a `WorkItem`; the capture points hold a `WorkItemContext`. And the two answers are not the same shape — which is the part a co-located sibling function does not solve. `OutageSourcePolicy` is 3-valued and, verified at `outage-notices.ts:18-26`, collapses `team-`, `callback:`, `event:` **and** `worker:` into one `silent` bucket, while D3's `waiting` needs that bucket split: `team-` ⇒ `agent`, the other three ⇒ `nobody`. **A `waitingFor` that projects from that 3-valued `OutageSourcePolicy` output therefore cannot exist**; recovering the split would need a second `startsWith` chain, which is exactly what C6 and AC4 forbid — and AC4's repository-wide test would fail the implementation as previously specified. Co-location is not the requirement. A shared *table* is.

So the extraction goes one level deeper than a rename, and it happens **inside `outage-notices.ts` itself**: the file's flat five-arm `startsWith` chain becomes one ordered prefix→bucket table with one predicate over it, and both public answers become total maps from the bucket. `policyForId` is a thin wrapper, not a peer.

```
type WorkItemSource = "cron" | "callback" | "event" | "agent" | "worker" | "human";

const SOURCE_PREFIXES = [["sched:","cron"], ["callback:","callback"], ["event:","event"],
                         ["team-","agent"], ["worker:","worker"]] as const;   // the ONE prefix table
function sourceOfId(id: string): WorkItemSource        // the ONE prefix predicate; fallthrough ⇒ "human"

policyForId(id)  = POLICY_BY_SOURCE[sourceOfId(id)]    // cron:skip · callback/event/agent/worker:silent · human:notify
policyFor(item)  = policyForId(item.id)                // unchanged behaviour, signature and callers
waitingFor(id?)  = id === undefined ? "nobody"
                                    : WAITING_BY_SOURCE[sourceOfId(id)]
                                                       // agent:"agent" · cron/callback/event/worker:"nobody" · human:"human-now"
```

Three properties make this a single source rather than two lists that agree today and drift tomorrow. `sourceOfId` is the only function in the repository that tests a reserved `WorkItem.id` prefix. Both projections are exhaustive `Record<WorkItemSource, …>` maps, so adding a prefix to the table is a **compile error** until both projections classify it — the drift is caught by the type checker, not by a reviewer. And neither projection can see a prefix at all, so neither can acquire a private one. The per-arm rationale comments in the current chain move onto the table's rows, where they stay attached to the prefix they explain.

`policyFor` is behaviour-preserving to the byte: signature, return type, `OutageSourcePolicy` and every existing caller are untouched, so this is a refactor of the outage path, not an API change to it. The existing outage-notice tests keep passing unmodified, and AC4 adds one table-driven case per prefix pinning the pre-refactor value.

**The `Waiting` type crosses as a type-only import** (`import type { Waiting } from …` in `outage-notices.ts`, the type itself declared in the ops module beside the envelope it belongs to). Type-only imports are erased, so this adds no runtime edge from `src/outage/` into the new ops module and no import cycle; the one runtime dependency stays ops → outage.

**AC4's repository-wide test needs exactly one allowlisted hit, and it is not a `WorkItem` id.** `src/agents/provider-adapters/sse.ts:36` contains `line.startsWith("event:")` — SSE field-name framing that shares a literal with a reserved id prefix by coincidence. It is allowlisted by path with the reason recorded inline, the `boot-order.test.ts` allowlist discipline: a deliberate, reviewed classification, never a way to silence a real hit.

**Read the prefix table, not the comment** — the stale *"team DM"* fallthrough comment is still at `:25`, and an implementer who trusts it maps agent-to-agent traffic to `human-now`, the misrouting this epic exists to remove. That comment is corrected in this diff (it moves onto the `human` row, where it describes what actually reaches it), since this ticket is the first consumer that would be misled by it.

**Absent `workItemId` ⇒ `nobody`**, fail-closed to the quietest value. That is not a fudge: a detached worker or scribe execution has no `WorkItem` because nobody is directly waiting on it (KPR-453 canon), so `nobody` is the true value, and the failure is still published in full. `waiting: obligation` is never derived here — D3 reserves it for KPR-456's sweep, the only component that knows a deadline exists. `policyFor`'s documented ws/app client-supplied-id caveat carries over unchanged; the blast radius is one event's `waiting`, hence one mis-selected subscription. **D6's admissibility bound deliberately does not cascade here**: it governs *storage*, and `waiting` is derived from whatever id the runtime holds, admissible or not. Letting an inadmissible id fall through to `waiting: nobody` would buy nothing against the caveat above — a hostile `team-…` id passes the charset anyway — while silently re-classifying honest ids whose only defect is an unstorable character.

### D8. Recovery, the open-condition map, and `generation`

D2 makes publishing recovery an **obligation**: without it a dismissed condition is permanently silent, because `generation` is an epoch over recovery and can never advance.

**The map, its single writer, and the identity each entry carries.** One process-global, capped `Map<family, { openSeq, dedupeKey, firstFailureAt }>` where `family = "hive-runtime:tool:<toolName>:tool-failed"`, evicted oldest-first at the cap. It lives on the publisher singleton (D9), not on a runner, because runners are per-turn and the condition is not.

**Each entry identifies one open interval, not merely a family**, and that distinction is what the recovery path turns on. `openSeq` is a process-wide monotonic integer assigned by the drainer at the moment it **creates** an entry — never reused, never re-assigned to an existing entry — and `dedupeKey` is the key of the failure that opened the interval. Neither is decoration: `dedupeKey` is what a recovery publishes as `clears`, and `openSeq` is what keeps "the same open interval" decidable even when a family closes and re-opens at the *same* `generation`, which is reachable whenever the epoch resolver's reads fault and it falls back to its last in-process value. An accepted failure that finds the family **already present leaves the entry untouched** — same `openSeq`, same `dedupeKey`, same `firstFailureAt` — because a repeat is the same open interval under D2's own rule: `generation` cannot advance while no clearing fact has been accepted, so a repeat's `dedupeKey` equals the entry's by construction, and a pending recovery for that interval must stay valid across it. `openSeq` resets with the process, which is sound because the queue and the map are in-process too: no job can outlive the counter it was stamped against.

**The map is mutated at accept time and only by the drainer.** Both sides — entry *creation* on an accepted failure insert for a family holding no live entry (a repeat leaves the existing entry exactly as it is, above), removal on an accepted `tool-recovered` insert whose identity check passed — happen inside the single drainer, after the insert returns. The turn thread never writes it; the capture points only *read* it, and the success path's read is a lookup for the entry's identity rather than a bare membership test. This is what makes D9's "the drainer serializes the open-condition map" literally true rather than approximately true, and it is the reason the ownership is stated once, here, and nowhere else in this spec.

Enqueue-time and accept-time removal are different mechanisms with opposite failure modes, not two phrasings of one thing, so the choice is made on those failure modes and stated once:

- **Remove at enqueue** (turn thread) makes the removal a promise the queue may not keep: a recovery job lost to overflow or to a publish fault leaves no clearing fact, so `generation` does not advance at that boundary. It also puts a second writer on the map, contradicting the paragraph above.
- **Remove at accept** (drainer) cannot lose the clearing fact — a faulted or dropped recovery job leaves the entry in place, so the *next* success re-enqueues and the boundary self-heals. Its own cost is that every success landing between a recovery's enqueue and its accept finds the family still present and enqueues another recovery job.

That cost is then removed — but **only by an identity check. A membership check is not sufficient, and specifying one is itself a defect.** The natural-looking "drop the recovery if nothing is open for this family" fails under a reachable interleaving, because the drainer is serial while the queue is not partitioned per family:

```
queue:  R1{clears:K0, openSeq:7}   F3   R2{clears:K0, openSeq:7}
                                        ↑ enqueued from a success whose map read
                                          happened before R1 drained
drain:  R1 → accept; clearing fact for K0; entry removed
        F3 → resolver sees that clearing as more recent → generation 1;
             entry CREATED at openSeq 8, dedupeKey K1
        R2 → has(family) is TRUE (the openSeq-8 entry) → publishes anyway
```

Three harms follow, and the third is the worst. The published `clears` names the dead `K0`, so KPR-468's clearing application targets an already-superseded row while the live one keeps nudging. The accept-time removal then deletes the openSeq-8 entry, so the **live** condition holds no open entry and no later success can ever enqueue a recovery for it — the permanent silence D2's epoch rule exists to prevent, reintroduced by the very mechanism meant to fix it. And the log is left holding a clearing fact *more recent* than the latest `tool-failed` for that family, so the next plain repeat resolves to `generation` 2 and mints a fresh ledger row beside the still-open one and re-notifies — precisely the flood C18 forbids, reached with no recovery having occurred at all.

**So the drainer's pre-publish test is `entry?.openSeq === job.openSeq`**, evaluated before any I/O, and the job is dropped — no publish, no map write, no clearing fact — on either failure: the entry is absent, or it is present under a different `openSeq`. Membership is not part of the test; identity subsumes it. Because the drainer is serial and is the map's only writer, nothing can replace the entry between that check and the accept-time removal that follows a successful publish, so the removal is unambiguously of the entry just verified rather than of whatever happens to be under the key.

The two drop reasons are counted separately, because they say different things about the system. **`recoveryCoalesced`** (entry absent) is the benign burst case the check was introduced for: a sibling recovery for the same open interval already closed it, so N successes in one drain window still yield exactly one `tool-recovered`, with no second structure and no turn-thread mutation. **`recoverySuperseded`** (entry present under a different `openSeq`) means the tool re-failed and re-opened before this recovery could be recorded — a signal about the tool, not about the queue, and one an operator reading the counters should not have folded into the coalescing count.

**The residual of a correct supersede-drop, with the ordering stated the right way round.** A dropped `recoverySuperseded` job discards a recovery observation that was never published, and it is worth being exact about what is discarded, because the ordering runs opposite to the intuitive reading. Enqueue is synchronous at each observation and the queue is FIFO, so **anything that drained ahead of this job was enqueued — and therefore observed — before this job's success**. Supersession requires the reopening failure to have drained between this job's enqueue and its drain, so that failure was observed *before* the success this job carries, never after it. The job's observation is therefore a **genuine** recovery of the live interval (`openSeq` 8): the tool's success **was observed after** the failure that reopened the family. That is observation order and not wall-clock order — with concurrent turns and differing hook latencies, a success observed later could have occurred earlier — which costs the argument nothing, because every fact downstream of this point is defined over published and observed facts, and which if anything makes the drop *easier* to justify rather than harder. What is stale is only the `clears` key the job carries, which names the interval that was open when the success was observed (`openSeq` 7) and that a sibling recovery has since closed. The drop discards a real but now mis-addressed recovery observation — not a false one.

So the cost of a supersede-drop is one delayed boundary *per occurrence*, and neither of the other two things a reader might fear. It loses no *evidence*: this producer publishes recoveries, not successes, so the success was never itself an event, and the tool's behaviour across that window stays fully readable from the failure rows the log already holds. It loses no *recorded* boundary: the one the job's `clears` names (`openSeq` 7) **is** recorded, by the sibling recovery that ran ahead of it. And it is not a *silence*: the live entry survives the drop, so the next success on that tool enqueues a fresh recovery carrying `openSeq` 8 and that boundary lands one cycle later. The delay is **one boundary per supersession, self-healing as soon as a recovery drains with no intervening failure** — which is a weaker claim than the restart and enqueue-window residuals below, and the difference is worth stating rather than smoothing over: those two are one-shot, while supersession is repeatable for as long as backlog persists, each occurrence pushing the boundary another cycle, so under *sustained* flap and *sustained* backlog together no clearing fact lands at all. The direction is still the one every race in this section errs in — a condition stays open too long, never a fact unrecorded — and `recoverySuperseded` makes that state visible instead of silent, which is why it needs no handling beyond its own counter.

**Re-targeting the job to the live entry was considered, and is declined.** Because the FIFO argument above shows the success was observed after the reopening failure, the drainer *could* ignore the job's carried `clears`, publish against the live `entry.dedupeKey`, and remove that entry — a true assertion, landing the boundary immediately instead of one cycle later. Two grounds against, and the **primary** one is not the churn argument an earlier round leaned on. The job's carried `clears` is a single fixed statement of what this recovery asserts, made by the observer that read the map at the moment of the success; re-targeting makes it a value the *drainer* rewrites between enqueue and accept, so the assertion published would be one no observer ever made. Holding that statement immutable is worth more than landing the boundary a cycle sooner — and dropping is a one-branch-reversible choice in a way that a rewrite, once readers depend on `clears` meaning "what the observer saw", is not. The churn ground is real but **weaker than previously stated here**: re-targeting would advance `generation` once per flap cycle, which is exactly the rate the contract already produces for a flapping tool when nothing is backlogged (D2's fail→succeed→fail rule), so it does not invent churn — it restores the un-backlogged rate. It survives only as a tiebreak: dropping errs toward *fewer* epoch advances precisely under load, which is the direction this epic's noise budget prefers. The conclusion is unchanged. ⚠ Delegated, non-blocking, and cheaply reversible — re-targeting is a change at this one drain-time branch if the delayed boundary ever proves to matter more than the churn.

**The cap delays a boundary by a different route, on the same bound.** If an entry is evicted oldest-first at the cap while a recovery for it is queued, that job drops (as `recoverySuperseded` if a failure has since re-opened the family, otherwise as `recoveryCoalesced`) and the evicted interval never receives a clearing fact. This is not a new failure mode introduced by the identity check — an evicted entry is unclearable by definition, since the success path finds nothing in the map to enqueue against — and it carries the identical bound to the restart and enqueue-window residuals below: one delayed epoch boundary, re-armed by the next failure→success cycle, never a lost fact.

Accept-time removal, under that identity check, is strictly better on both axes, which is why it is the one this spec pins.

**On success** (`PostToolUse`; Lane B's `:350`): a map read and nothing else. If the family is absent — the overwhelmingly common case — the observation returns immediately. **No database read on the success path**, per D2's explicit rejection of one against C15. If the family is present, one `tool-recovered` job is enqueued carrying **both** halves of the entry's identity: its `dedupeKey`, which the job publishes as `clears`, and its `openSeq`, which is job-local bookkeeping checked at drain and **never stored on the event** — D2's key set is closed and `openSeq` is not in it. The entry is removed later, by the drainer, if and when that publish is accepted, and only if the identity check below passed.

**`waiting` on the recovery publish is the fixed value `nobody`, not a derived one.** `waiting` is required and producer-supplied per event (D2), and this is the one publish where deriving it would be wrong rather than merely awkward: the succeeding turn is an arbitrary later turn that has nothing to do with the turn that failed, so `waitingFor` would attribute that stranger's waiter to a recovery. Worse, it would let an `informational` recovery be selected by a subscription filtering `waiting: human-now` — a subscriber asking to hear about things blocking a live human would receive tool recoveries. `nobody` is also simply true: a recovery blocks no one, which is what `class: informational` already asserts. The failure publish keeps the derived value (D7).

**On failure**: the epoch resolver runs **two bounded indexed reads** over the family — the latest event under `reasonId: "tool-failed"`, and the latest event whose `clearsFamily` equals the family.

**"Latest" and "more recent" are the compound order `(publishedAt, _id)`, never `publishedAt` alone.** `publishedAt` is a single server clock at millisecond resolution (D9 step 7), and the serial drainer can stamp a failure and a clearing event inside the same millisecond under exactly the storm this queue exists to absorb. On an exact tie "more recent" is undefined, so `generation` advancement would be nondeterministic — a live C18 hazard, since that criterion demands deterministic advancement on real recurrence-after-recovery and only there. The compound key is a true total order and it is the *right* tie-break rather than an arbitrary one: the drainer is the single writer, so insertion order **is** publish order, and a Mongo `ObjectId` carries a per-process counter that increments within a millisecond, so `_id` orders same-millisecond siblings in the order they were published. **Which side mints that `ObjectId` is worth naming, because the argument rests on it:** the producer never supplies `_id` — which is all KPR-458 D2's "Server-assigned" row asserts — and the Node driver therefore generates it **client-side**, in this process, at insert (its default; `forceServerObjectId` is not set). The incrementing counter is thus the drainer's own, in the drainer's own serial order. The argument survives the other reading too: were `_id` minted server-side, a single serial client would still deliver these inserts in publish order to one `mongod` counter. The total order does not depend on choosing between them, only on the drainer being serial and sole. This is the same total order D12's cursor uses (`{ publishedAt: 1, _id: 1 }`), and both epoch-read indexes carry `_id: -1` as their final key so each read's sort is index-covered.

If the clearing fact is the more recent under that order, `generation` is the latest condition event's plus one; otherwise it is that event's unchanged, or `0` when there is none. **If either read faults the publish still proceeds**, contained, at the producer's last in-process value for that family (D2) — **and that value is read off the open-condition entry, never out of a second structure.** The entry's `dedupeKey` embeds the generation of the interval it opened, so a faulted resolve returns that entry's generation, and `0` when the family holds no entry.

That choice is not incidental. A separate per-family fallback map would be a second structure over an unbounded key space — `mcp__<server>__<tool>` across every installed plugin — needing its own cap and eviction rule, and it would slow-leak under exactly the failure storm this mechanism exists to survive. Worse, it could evict independently of the open-condition entry and hand back a generation the live entry contradicts. Reading the entry means there is **exactly one** such structure, already capped and evicted oldest-first (above), and it is what makes the by-construction claim earlier in this section literally true rather than nearly true: on a repeat the resolver yields the entry's generation whether its reads succeeded — the latest condition event under that reason **carries the entry's generation**, since every event published during a live interval carries that interval's generation (a repeat is later than the opening failure and still carries it), and no clearing fact can be more recent while that entry is still live, since an accepted clearing fact removes it — or faulted, where the fallback reads the entry directly. A repeat's `dedupeKey` therefore equals the entry's on both paths. The `0` fallback is reached only where there is no entry to read: a first failure, one whose entry was evicted at the cap, or a family reopening after a recovery. That last case is D2's named residual — a bounded mis-attachment of a notification, never a lost fact, because the log append is unconditional.

**Restart residual, carried from D2 unchanged.** The map empties on restart, so a condition raised before a restart gets no clearing fact when it next succeeds and its epoch does not advance at that boundary; the following failure→recovery cycle re-arms it. One lost epoch boundary per restart per open condition, never a lost fact.

**Enqueue-window residual, the price of accept-time entry, and the same shape.** A success landing between a failure's *enqueue* and its *accept* reads a map that does not yet hold the family, so it enqueues no recovery; the failure then accepts and opens the condition for a tool that has already recovered, and the condition stays open until the next failure→success cycle closes it. This is the restart residual's exact shape and bound — one delayed epoch boundary, never a lost fact, since both events are appended to the log regardless — and it is accepted for the same reason: the alternative is entering the family from the turn thread, which reintroduces the second writer this section exists to eliminate. Every race in this section errs toward a condition staying open one cycle too long, never toward a fact going unrecorded.

`generation` never advances because the condition recurred, because time passed, because a nudge went unanswered, or because a turn retried (C18). A test asserts a repeated identical failure leaves `generation` unchanged, and that failure → success → failure advances it by exactly one.

### D9. The accept path, and how it stays off the turn

**Order inside one publish**, all of it inside the publisher, none of it on the turn's await path:

1. Resolve the registry row for `(producer, reasonId)`; unknown or `enabled: false` ⇒ reject + count (C5).
2. Validate `subject` against D4's bounds, `detail` against the row's `detailKeys` zod schema, and `evidence` as `{kind, id}` references only ⇒ reject + count on any breach (C5, C13).
3. Stamp `class` and `retry` **from the row**; a submission asserting either is rejected (C4). The `observe*` call sites cannot supply them — the internal API has no such parameters.
4. When `clears` is present, check its legality and derive `clearsFamily` from it. A `clears` whose reason declares no `clearsReasonIds`, or names a reason outside that list, is rejected (C19). Neither half needs *this* event's `generation`: the legality check reads the registry row, and `clearsFamily` is the incoming key with its own generation component stripped — which is why this step can precede the next one.
5. Resolve `generation` — **on a failure publish only.** D8's resolver is defined "on failure", and its two indexed reads exist to find a clearing fact for a *condition* family; running them for a recovery would be two reads whose answer is never used. A `tool-recovered` publish skips the resolver and carries **`generation: 0`, always**: this producer declares no advance rule for its clearing reason, and D2's rule for a reason with none is that it holds `generation` at `0`. The consequence is deliberate: every recovery for one tool shares the `dedupeKey` `hive-runtime:tool:<tool>:tool-recovered:0`, so once KPR-468 exists a repeated recovery renews one informational ledger row (D7 rule 4) instead of minting one per recovery — which is the right behaviour for a fact nobody is expected to subscribe to. It collides with nothing: the recovery's own family (`…:tool-recovered`) is distinct from the family its `clearsFamily` names (`…:tool-failed`), and it is the latter that D8's clearing-side read matches on. **Then, and only then, derive `dedupeKey`.** D2's formula is `producer:subject.kind:subject.id:reasonId:generation`, so the key cannot exist before the epoch it embeds does — and the error would not stay local to one event: the derived key is what D8 stores on the open-condition entry and what a later recovery publishes as `clears`, so deriving it ahead of this step would stamp every event, every map entry and every clearing fact with an unresolved generation.
6. **Evaluate the match** — a pure, I/O-free conjunction of set-membership tests over the D5 grammar against the **loaded** subscription set. No operators, no negation, no wildcards, no nesting.
7. **Stamp the two server-owned envelope fields**, neither of them producer-supplied: `schemaVersion` — **initial value `1`** — and `publishedAt`, the server clock read at accept. D2 makes `schemaVersion` required and additive-only and binds readers to ignore unknown fields and to infer nothing from absence, so it is written on the very first document rather than back-filled: KPR-455 and KPR-468 read this shape, and a log whose earliest rows lack the version field forces every future reader to special-case them.
8. **One immutable insert** into `ops_events` carrying `matchedSubscriptionIds` and its length as `matchedSubscriptions`. Zero is a stored, queryable fact and never a failure (C2, C3). Nothing re-evaluates the match afterwards; KPR-468's sweep reads the stamped list.

The complete stored key set is therefore D2's table entire: `_id`, `schemaVersion`, `publishedAt`, `producer`, `reasonId`, `class`, `retry`, `waiting`, `subject`, `generation`, `dedupeKey`, `detail`, `evidence`, `matchedSubscriptions`, `matchedSubscriptionIds`, plus `clears` and `clearsFamily` on a clearing event only. Nothing else is written, and D2's explicitly-absent list (`owner`, `severity`, `destination`, `recipient`, any rendered string) is enforced by the same schema that enforces `detail`.

**The loaded subscription set.** Loaded at boot, refreshed on a **60 s** periodic reload and on `SIGUSR1` — **the existing handler at `src/index.ts:575`, extended in place, never a second `process.on("SIGUSR1", …)` listener.** That handler already flushes the prefix cache and reloads the registry; the reload call is added to its body. It sits *below* the spawn-capable boundary, correctly and without exception: a signal handler is not a per-spawn read, and the publisher's own wiring — the thing a turn reads — is above the marker (D10). The reload timer is `unref()`ed at creation and cleared in `stop()`, the `outage-replay-processor.ts:44` precedent — an ops-diagnostics timer must never be the thing holding the process open, and a timer surviving `stop()` fires against a closing Mongo client. ⚠ The 60 s value is delegated and non-blocking. D12 already rules that a reload lag means a just-registered subscription may miss an event by seconds and that this is not a new failure mode, because D5 forbids retrospective enrolment either way. A reload fault leaves the previous set in place and counts; it never empties the set, because an empty set silently makes every event a zero-match.

**Off the turn, and not fire-and-forget.** `observeToolFailure` / `observeToolSuccess` are **synchronous, non-throwing, and return void**. They do the map lookup (success) or enqueue one job (failure/recovery) onto a bounded in-process queue drained by a single worker. This is chosen over an unawaited promise for four reasons, all real: the failure path performs two indexed reads and a write, which under a storm would otherwise open unbounded concurrent Mongo work from inside a turn; the drainer serializes per-family epoch resolution against the map; a bounded queue has a drop policy and a counter, where an unawaited promise has neither; and shutdown has something to drain (the KPR-456 `inFlight`-set precedent). Overflow drops the **oldest** and increments a counter — a full queue means a storm, and the newest failures are the ones a responder needs.

**Containment (C15).** Every observe call is wrapped so that no throw escapes to the tool path; the drainer catches per job, counts, and continues; a Mongo fault degrades to warn-and-count. This is the discipline KPR-452 D4 imposed on the audit path, for the same reason and with more at stake: the Lane B site sits inside the one method whose header promise is "structurally cannot throw", and the Claude-lane sites sit in hook callbacks the SDK awaits mid-turn. Two tests are negative-verify: a publisher that throws on every call leaves a turn's `RunResult` byte-identical, and a publisher whose Mongo is down does the same.

**D10 invariant (a), which earns its keep here.** A publish fault, a validation rejection, a match failure or a queue overflow is **logged and counted, never published**. Counters live in memory behind a `getSnapshot()` for a later reader; no telemetry document, no doctor section, no event about the ops path ships in this ticket. **That `getSnapshot()` has no caller in this diff, deliberately — it is not scope creep toward KPR-455.** It is the KPR-220 spawn-coordinator precedent, where the snapshot surface shipped ahead of the heartbeat and the doctor section that later read it: shipping the accessor alongside the counters is what keeps the counter set a defined surface rather than ad-hoc fields, and it gives KPR-455 something to read without reopening this file. Invariant (b) is trivially satisfied — this child delivers nothing and spawns nothing.

### D10. Boot order, indexes, and shutdown

**Above the boundary.** Publishing is read per spawn — the first turn after boot can fail a tool — so the publisher's construction, `init()` (collections + indexes) and singleton registration all sit in `index.ts`'s above-boundary wiring block (`:404-473`), beside the KPR-394/414/417 wiring, and **above** the `// ── Spawn-capable boundary ──` marker at `:474`. Its anchors go in **all three** lists of `src/boot-order.test.ts` — presence (a), order (b), and the superset-sweep bound (c) — per the engine-wide rule; adding to (a) alone is the failure mode that guard exists to catch.

The publisher is reached from the capture points through a **module-global singleton** with `setOpsPublisher()` / `opsPublisher()` and a test reset, the `provider-registry.ts` precedent (a module-global registry set once at boot, because the consumer is module-scope). Unset ⇒ every observe call is a no-op, which is what keeps the pre-wiring boot window and every bare test construction correct by construction rather than by ordering luck.

**`init()` never fails engine boot, and the split follows the engine's own precedent rather than a blanket rule.** The repo does not treat index creation uniformly: `MeetingWorkerPool.ensureIndexes()` is awaited boot-fatal because the claim ledger's partial-unique index *is* its atomicity, while `MeetingScribe.ensureIndexes()` is `.catch`-logged at `index.ts:456` with the reason stated in the comment there — a TTL index with "no correctness role", where making an always-degradable feature boot-fatal would contradict the feature's own degrade rule. **Every index this ticket creates falls on the scribe side of that line**: the two epoch-read indexes and the cursor-order index are performance (a collection scan returns the same answer), the TTL index is housekeeping, and `ops_reasons` uniqueness is already structural because `_id` is `"<producer>:<reasonId>"` — the unique index restates it rather than establishing it. So:

- **Index creation is individually contained**: each `createIndex` is `.catch`-logged and counted, and a fault does **not** prevent the publisher from being set. This matters concretely for the TTL index, which throws `IndexOptionsConflict` if it already exists with a different `expireAfterSeconds` — the exact thing that happens the first boot after an operator changes `config.activity.retentionDays`. A retention change must not silently switch off failure recording; the remedy is to drop the index (or `collMod` it) and restart, and the counted warning is what tells the operator that.
- **A fault in the reason-registry upsert leaves the publisher unset**, and boot continues. Every observe call is then the no-op the paragraph above already defines, which is the honest degrade: with no registry rows, C5 would fail-closed on every single publish, so a wired-but-registryless publisher would spend a rejection counter — the signal D9 reserves for a *mis-integrated producer* — on what is actually a Mongo outage.
- **Nothing here is fatal to boot.** An ops-diagnostics feed that can prevent the engine from starting is a strictly worse failure than one that is absent, and "unset ⇒ no-op" is already this spec's defined safe state everywhere else. The one loud failure mode is D5's enable gate, which is a pure precondition over the code-resident table with no I/O and fires only in development.

**Indexes** created in `init()`, the `obligations/store.ts:78-84` shape:

| Collection | Index | Purpose |
| --- | --- | --- |
| `ops_events` | `{ producer: 1, "subject.kind": 1, "subject.id": 1, reasonId: 1, publishedAt: -1, _id: -1 }` | D8's condition-side epoch read; `_id` is a key rather than an afterthought because the resolver's comparison is the compound `(publishedAt, _id)` order, which this index then covers instead of forcing an in-memory sort |
| `ops_events` | `{ clearsFamily: 1, publishedAt: -1, _id: -1 }` (sparse) | D8's clearing-side epoch read, in the same `(publishedAt, _id)` order the resolver compares |
| `ops_events` | `{ dedupeKey: 1, publishedAt: -1 }` — **not unique** | D2: the log appends every publish |
| `ops_events` | `{ publishedAt: 1, _id: 1 }` | D12's cursor order, created by the publisher because D12 assigns `ops_events` and its indexes here |
| `ops_events` | `{ publishedAt: 1 }`, `expireAfterSeconds` from `config.activity.retentionDays` | D9's "aligned with existing activity-history retention" |
| `ops_subscriptions` | `{ enabled: 1 }` | the loaded-set read |
| `ops_reasons` | `{ producer: 1, reasonId: 1 }` unique | C5's fail-closed lookup |

**The two `publishedAt`-leading `ops_events` indexes are both required and must not be consolidated.** `{ publishedAt: 1, _id: 1 }` and `{ publishedAt: 1 }` share a prefix, which reliably invites a later "the second is redundant" cleanup — it is not. A TTL index must be **single-field**: MongoDB refuses `expireAfterSeconds` on a compound index, so the cursor index cannot carry the TTL. And dropping the cursor index in favour of the TTL one costs D12's reader its covered `(publishedAt, _id)` sort. Neither is a subset of the other in any sense that matters; the clause is here so a future consolidation has to argue with this line first.

**Shutdown** drains the queue before Mongo closes, the KPR-456 ordering (`index.ts:943`). `stop()` clears the subscription-reload timer and stops accepting new jobs first, then drains — a reload firing against a closing Mongo client is a warned-and-counted fault for no benefit. Draining is bounded; on timeout the remainder is dropped and counted, because a shutdown that blocks on an ops queue is worse than a lost diagnostic row.

**No `boot-order.test.ts` anchor is added for anything KPR-468 owns** — `ops_notifications` and the sweep bring their own, and the sweep starts *after* transport adapters, which do not exist yet.

### D11. Boundaries — what this child deliberately does not touch

- **`agent_events` is unchanged**, including `EVENT_SCHEMAS`, `Scheduler.checkEvents`, and the `subscribe: string[]` agent-definition field. **The ticket's `system:task_blocked` widening is out of scope and superseded**: it was scaffolding for the rejected store-only mechanism, its `owner` field collides head-on with D2's explicitly-absent list and with the operator's "no owner on the event" ruling, and the coordination block it was meant to enrich is `hive-agent` / `coordination-block` in D4's example table — a *future* producer with an agent-facing publish tool that D10 gates behind `delegateServers` and worker containment and that this ticket does not build. ⚠ Non-blocking; if richer coordination-bus payloads are still wanted they are a separate ticket against a bus this epic is not changing.

The worker cannot *choose* to publish, sees no tool for it, and controls no field: the runtime publishes about it, through an allow-list, to a collection with no delivery attached. No outbound surface opens.

- **No `hive doctor` section, no CLI, no reader, no view.** Anything that reads `ops_events` is KPR-455.

## Conformance and acceptance criteria

Each maps to a KPR-458 criterion; each is testable at this child's boundary.

1. **AC1 (C1, C4)** — A published event carries no `owner`, `severity`, `destination`, `recipient` or rendered string, and `class`/`retry` equal the registry row's. The internal observe API has no parameter that could supply them; a test asserts the stored document's key set is exactly the D9 list — including `schemaVersion === 1` and a server-stamped `publishedAt` — with `clears`/`clearsFamily` present on a `tool-recovered` document and absent on a `tool-failed` one, and fails on any extra key. `evidence`'s **contents** are pinned too, not just its presence (D6): `[{ kind: "workItem", id }]` on a failure carrying a work item, `[]` on a failure without one, and `[]` on every `tool-recovered`.
2. **AC2 (C2, C3)** — With `ops_subscriptions` empty, a tool failure stores exactly one `ops_events` document with `matchedSubscriptions: 0` and `matchedSubscriptionIds: []`. The document is byte-identical in shape to a matched one. Nothing writes a ledger row, and no catch-all subscription is created by any code path.
3. **AC3 (C5)** — A disabled or unknown `(producer, reasonId)`, an undeclared `detail` key, an over-bound `detail` value, a non-scalar value and an over-length `subject.id` each reject the publish and increment the rejection counter. D6's `evidence` bounds are tested on the same footing, since they are validated at the same step: an array of more than 4 references, a reference whose `id` exceeds 200 characters, and one whose `kind` fails the `^[a-z][a-z0-9-]{0,39}$` token bound each reject and count. No coercion to a generic reason, no truncation of `subject.id`, and no truncation or trimming of `evidence`. **The omit path is then pinned *against* the reject path, because conflating the two is the defect this criterion now guards.** A client-supplied `workItemId` or `threadId` that fails D6's `^[A-Za-z0-9_.:#+-]{1,200}$` admissibility bound — a space-bearing value, an over-length one and a prose-shaped one are each driven, through the ws/app path that supplies them — publishes the event normally with that detail key **omitted**, with `evidence: []` where the work item was the omitted value, with `idOmitted` incremented and with **the rejection counter unchanged**. A `sched:` id carrying a multi-word cron task label takes the same path and is asserted to.
4. **AC4 (C6)** — `waiting` is produced by `waitingFor` in `src/outage/outage-notices.ts` over the single prefix→bucket table (D7), and `policyForId`/`waitingFor` are both total maps from `sourceOfId`'s bucket rather than independent prefix chains. A repository-wide test asserts `sourceOfId` is the only reserved-prefix `startsWith` test in the repository, allowlisting by path the one coincidental hit — `src/agents/provider-adapters/sse.ts:36`'s `line.startsWith("event:")`, SSE field-name framing that shares a literal with a reserved id prefix — with its reason recorded inline. All six mappings are pinned, `team-` ⇒ `agent` explicitly, and `policyFor`'s pre-refactor output is pinned per prefix so the extraction is provably behaviour-preserving.
5. **AC5 (C7, and C17's no-I/O clause)** — Match evaluation implements exactly the D5 grammar; a test enumerates it and fails any operator, negation, wildcard or nesting. **C17's other half — "only match evaluation is synchronous with publish, and it performs no I/O" — is pinned rather than asserted in prose:** a test evaluates the match against an in-memory loaded subscription set with the database handle instrumented to throw on any access, and asserts the match returns its result with the handle untouched.
6. **AC6 (C13)** — No stored field contains message text, tool arguments, a raw error, a URL, a path, a credential or prose. Negative test: a failure whose error text embeds a token-shaped string and an absolute path publishes a document in which neither substring appears anywhere. **The same test covers the untrusted-id path (D6), which is where C13 was not previously true by construction:** a failure on a turn whose ws/app-supplied `workItemId` and `threadId` carry prose publishes a document in which no substring of either appears — the key omitted rather than stored under a length bound.
7. **AC7 (C14)** — A publish fault, rejection or overflow produces a log line and a counter increment and **no** `ops_events` document. No code path in this diff spawns a turn.
8. **AC8 (C15)** — Negative-verify: with a publisher that throws on every call, and again with one whose Mongo write always rejects, a Claude-lane turn and a Lane B turn produce byte-identical `RunResult`s to a run with no publisher wired, and the turn's own error/abort classification is unchanged.
9. **AC9 (C18)** — A repeated identical failure leaves `generation` unchanged and appends a second event; failure → success → failure advances `generation` by exactly one and publishes exactly one `tool-recovered` in between, carrying `waiting: "nobody"` and `generation: 0` — the recovery never runs the epoch resolver (D9 step 5), so two successive recoveries for one tool share a `dedupeKey` and a third failure's `generation` is unaffected by how many recoveries preceded it. A burst of N successes enqueued before that recovery drains still yields exactly one `tool-recovered` and N−1 `recoveryCoalesced` counts. A recovery job whose sibling already closed the interval **and whose family has since re-opened under a new `openSeq`** is dropped as `recoverySuperseded`: a test drives D8's exact `R1 · F · R2` interleaving and asserts that no clearing fact names the dead `dedupeKey`, the live interval's map entry survives, a following plain repeat leaves `generation` unchanged, and the next success on that tool still enqueues a recovery. A recovery job whose publish faults leaves the family open so the next success re-enqueues it. A success with no open condition performs no database access at all.
10. **AC10 (C19)** — `tool-recovered` carries `clears` and `clearsFamily`; a `clears` published under `tool-failed` is rejected. Boot upsert refuses to leave `tool-failed` enabled if no registered row lists it in `clearsReasonIds`.
11. **AC11 (lane parity)** — The same underlying tool failing on the Claude lane and on Lane B produces the same `subject.id`, including for a tool whose name exceeds the Lane B sanitization threshold.
12. **AC12 (abort discipline)** — An own-abort (deadline or operator) mid-tool publishes nothing on either lane. A foreign interrupt publishes `errorSig: "interrupted"`. A guardrail deny publishes nothing.
13. **AC13 (boot order, boot survival, and hook placement)** — `src/boot-order.test.ts` carries the publisher's two anchors — the literal strings `await opsPublisher.init()` and `setOpsPublisher(` — in **all three** of its lists: `(a)`'s presence pass, `(b)`'s `wiringOffsets` array, and `(c)`'s `wiringStart` `Math.max` set, whose superset sweep is bounded by the **latest** wiring anchor. The publisher deliberately exposes **no `.start(`-spelled method** — the drainer and the subscription-reload timer are both armed inside `init()` — so `(c)`'s `allowlist` needs no new entry; a later refactor that introduces `opsPublisher.start(` must either place it after the wiring anchors or add it to that allowlist under the reviewed-classification discipline the list's own comment demands. The test fails if the wiring moves below the marker. With the publisher unset, both capture points are no-ops and no turn is affected. An `init()` whose `createIndex` calls all reject still yields a wired, publishing publisher; an `init()` whose registry upsert rejects yields an unset publisher and a booted engine — neither throws out of boot. **And a structural test pins that the two new hook matchers are registered outside the archetype `PreToolUse` `try`/`catch`** (KPR-458 D2 rule 3): a thrown archetype build must still leave both observers registered, and a thrown observer registration must still leave the fail-closed deny-all matcher installed. The plan writer carries this as a placement requirement, not a style note — the two are adjacent in `buildHooks` and collapsing them into one `try` silently couples a diagnostics feed to a security gate in both directions.
14. **AC14 (documentation)** — `CLAUDE.md`'s engine-written collections list gains `ops_events`, `ops_subscriptions` and `ops_reasons`, each with its key, index and TTL posture.
15. **AC15 (C12)** — Outcome is published, never inferred. Every `tool-failed` event originates in a failure *signal* — `PostToolUseFailure`'s payload on the Claude lane, the thrown value in `wrap()`'s `catch` on Lane B — and no code path in this diff reads `costUsd`, a turn or tool duration, an elapsed-time threshold, or a `PostToolUse` `tool_response` to decide that something failed. Tests: a successful tool call publishes no `tool-failed` regardless of its duration or its turn's cost; `PostToolUse` publishes only `tool-recovered`, and only when the map holds an open condition. `activity_log` is neither read nor written here (D11). This is the criterion the "verify at implementation" probe below reports against — a Claude-lane failure class that does not fire `PostToolUseFailure` is left uncaptured rather than inferred.
16. **AC16 (C16)** — Adding a reason, a producer or a subscriber stays data rather than an engine change, and this child's accept path is what has to hold that true. A test registers a second `ops_reasons` row under a different `reasonId`, and one under a different `producer` token, then publishes against both through the same accept path: both are stored, each stamped with its own row's `class`/`retry` and validated against its own `detailKeys`, with no edit to the envelope, the filter grammar or the observe API. `producer` and `reasonId` are validated by D2's pattern bound and never against a hardcoded list — the only legitimate occurrence of the literal `hive-runtime` is in this producer's own code-resident rows, never in a validator. A subscriber is added by inserting an `ops_subscriptions` row and waiting one reload, which AC5's grammar test exercises over a set loaded from the collection rather than from a fixture constant.

- **⚠ Delegated (non-blocking) — `subject.kind: "tool"`, not `"workItem"`.** D2 discusses a workItem subject as its worked example; this producer keys on the tool because the condition is "this tool is failing" and D8's own view keys on `detail.tool`/`detail.errorSig`. Cost: one condition per tool across all agents and all error tokens. The alternative (`<tool>#<token>`) is a one-line change bounded by a nine-value set. D4.

Boot upsert never overwrites `enabled`. The simpler alternative — a code constant — would make C5 implementable but would forfeit the operator lever and Florist's ability to add rows without an engine change, which D4 names as the registry's whole point. - **⚠ Delegated (non-blocking) — `tool-failed` is `retry: transient`.** The population is mixed; `transient` is the honest default, and D3's stated lever for a deterministic class is a second `reasonId`. D5.

Needed because `ToolBridgeOptions.agentId` is the display name, which D5 forbids as identity. Absent ⇒ the detail key is omitted. D6.
- **⚠ Delegated (non-blocking) — untrusted ids are bounded to an admissibility token and *omitted*, not rejected.** Round-4 review found C13 not true by construction for the only three stored values authored outside this producer — `detail.workItemId`, `detail.threadId`, `evidence[].id` — since the ws/app channel supplies the first two behind a bare `typeof === "string"` (`ws-adapter.ts:262`/`:563`, validated at `ws/protocol.ts:228`/`:235`) and `sched:` ids embed the operator's free-form cron task label (`scheduler.ts:231`/`:236`). - **Non-blocking, corrects the draft — `agentId` is dropped from `tool-recovered`'s `detailKeys`.** Round-4 review found the third instance of an attribution this spec had already refused twice on the same event type: the only agent slug reachable on the recovery path belongs to the arbitrary later turn whose success triggered it, which is the same stranger whose work item the spec refuses as `evidence` and whose waiter it refuses in favour of a fixed `waiting: nobody`. - **⚠ Delegated (non-blocking) — bounded queue rather than an unawaited publish.** Justified in D9 on four counts. Overflow drops oldest and counts; shutdown drains with a bound.
- **⚠ Delegated (non-blocking) — the open-condition map is drainer-owned, mutated only at accept time, and each entry carries an identity.** Round-2 review found the draft asserting both accept-time and enqueue-time removal. Resolved to accept-time on failure modes (D8): enqueue-time removal can lose a clearing fact outright, accept-time removal cannot, and its only cost — duplicate recovery jobs in the drain window — is erased by the drainer's **identity** check, `entry.openSeq === job.openSeq`. Round-3 review established that a membership check (`has(family)`) cannot do that job: it passes for an entry belonging to a *later* open interval, and the stale job then publishes a clearing fact for a dead epoch, deletes the live interval's map entry (permanent silence, the exact defect accept-time removal was fixing) and leaves a clearing fact more recent than the latest failure, so the next plain repeat advances `generation` — the C18 flood, reached with no recovery. Each entry therefore carries `openSeq` (a process-wide monotonic integer assigned only when an entry is *created*) and the opening failure's `dedupeKey`; an accepted repeat leaves the entry untouched, because a repeat is the same open interval. Costs accepted, both bounded to one delayed epoch boundary: entry is also accept-time, so a success landing inside a failure's enqueue window leaves the condition open one cycle longer; and a correctly superseded recovery is discarded rather than re-targeted, reasoned in D8. Round-4 review corrected the ordering argument under that last cost: FIFO enqueue plus a serial drainer means everything draining ahead of a recovery job was observed before that job's success, so a superseded job holds a **genuine** recovery of the live interval (the reopening failure was observed first) carrying a stale `clears`, not a false recovery. The drop is therefore a one-cycle delay, not a lie avoided; re-targeting to the live entry would be sound, and is declined in D8 on noise grounds — supersession only occurs under backlog, and re-targeting maximizes epoch churn exactly there. The same round removed the epoch resolver's separate fault-fallback value: it is read off the open-condition entry's own `dedupeKey`, so there is one capped structure rather than two and the by-construction `dedupeKey` equality holds on the faulted path too. Round-5 review refined three statements in that reasoning without changing any decision: the supersede residual is **one delayed boundary per supersession**, repeatable while backlog persists rather than carrying the one-shot bound the restart and enqueue-window residuals do (and `recoverySuperseded` is what keeps that visible); the FIFO argument establishes **observation** order rather than wall-clock order, which the drop does not need and which makes it easier to justify, not harder; and the re-targeting decline now rests primarily on `clears` staying a fixed statement made by the observer that read the map, with the churn ground demoted to a tiebreak because re-targeting restores the contract's ordinary un-backlogged flap rate rather than inventing churn. D8.
