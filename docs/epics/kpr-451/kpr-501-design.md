# KPR-501 — Agent-facing block producer: `hive-agent` publishes coordination and semantic blocks into `ops_events`

## TL;DR

KPR-501 is the **second producer** on KPR-458's contract. It gives every agent two tools on the existing in-process `event-bus` MCP server — `report_block` and `clear_block` — that publish, through the already-shipped `OpsPublisher` accept path, the two facts Gate 1 said only an agent can see: *I am blocked on another party's act* (`coordination-block`) and *I cannot proceed without a decision above my authority* (`semantic-block`), plus the clearing fact that closes either (`block-cleared`). The condition is keyed on the agent's unit of work — `(agentId, threadId)` — never on the turn, so a block raised in one turn is cleared from a later one; the open condition is resolved from the log, not from in-process state, so it survives restarts. No new server, no new collection, no new loader, no notification, no turn spawn: shipped alone it is staged exactly as KPR-454 was — every block recorded, none delivered, `matchedSubscriptions: 0` — and it is what fills KPR-455's ack-edge arm 1.

## Key Points

- **Smallest surface that satisfies the charter: two tools on the existing `event-bus` in-process server, not a new server.** `event-bus` is already in `IN_PROCESS_PORTED_SERVERS`, already in `WORKER_SERVER_DENYLIST`, already has a stdio placeholder so the Lane B inventory bridges it, is not auto-injected (so none of the three `suppressAutoInjectedServers` gates change), binds the agent id at construction, and already holds the runner-owned `WorkItemContextRef`. Both KPR-390 standing obligations are satisfied by inheritance and are asserted on the runner's **built** server set, not argued (D2).
- **Three reason rows ship with this producer, under `producer: "hive-agent"`:** `block-cleared` (`informational`, clears both, upserted first), `coordination-block` (`resource` / `deterministic`), `semantic-block` (`judgment` / `deterministic`). ⚠ Delegated: `coordination-block` is `resource`, not the `judgment` KPR-458's illustrative table showed, because a coordination block is cleared by the agent itself when the awaited act arrives, which is D3's `resource` clearing act; `semantic-block` is the one that needs a named human's ruling (D3).
- **The subject is the agent's work unit, not the turn.** `subject: { kind: "agent-work", id: "<agentId>:<threadId>" }`, falling back to `"<agentId>"` when the thread id is not storable. KPR-453 canon says a work-item id "proves neither unique attempt nor task continuity", and Gate 1's own storage note says a later turn "needs an explicit link to the blocked work" — the engine's link is the thread (the per-thread lock and session key). `workItemId` rides `detail` and `evidence` as the identity of the raising or clearing turn (D4).
- **Agents state facts, never axes.** `class`/`retry` come from the registry; `waiting` is `waitingFor(workItemId)` from the one prefix table (C6), never a tool parameter; `agentId`, `workItemId`, `threadId` are read from constructor state and the live `WorkItemContextRef` at execution, never from the agent. The tool's parameters are closed enums plus two references: `rulingRef` under a closed three-shape grammar (a Slack ts, a conversation-qualified ts, or an issue key) and a same-agent `threadId` override that can only *name* an engine-composed family, never store a new string. **Every value rule is enforced in the handler, not in the declared schema:** the SDK `tool()` shape is wrapped by the MCP layer into a non-strict `z.object` whose failures answer as an `isError` result *before* the handler runs, so the declared shape carries types and optionality only, and a bad value is a handler-visible `{ state: "refused", reason }` with a counter — never an MCP-layer validation error. No free text is stored anywhere (D5, D6).
- **The clearing fact is log-resolved and class-honest.** `clear_block` reads the open condition from `ops_events` with the same two indexed `(publishedAt, _id)` reads the epoch resolver uses, publishes `block-cleared` with `clears: <exact open dedupeKey>`, and refuses a `semantic-block` clear that carries no ruling reference — a KPR-458 D3 class rule (a `judgment` condition is closed by a named human's ruling, so the clearing fact must cite one), enforced at the tool because the ledger's `evidence.length >= 1` floor is only a floor: on an admissible turn the clearing turn's own `work-item` reference would satisfy it without any ruling (D7). No open block ⇒ no publish (D2's "a clearing fact for a condition never raised is noise").
- **Every publish rides the single serial drainer.** A new accept-only job kind on `OpsPublisher` (`enqueuePublish`) carries both tools' events onto the same bounded FIFO the capture points use; nothing in this child inserts into `ops_events`, and a repo-wide guard test pins that. This is what preserves the `(publishedAt, _id)` publish/drain order KPR-468's cursor consumes — a synchronous side-door insert could land behind an advanced watermark and be skipped forever (D8).
- **The ops path still publishes nothing about itself and spawns no turn.** Every answer the handler *returns* — `queued`, `no-open-block`, `refused`, `disabled`, `unavailable` (publisher unset) **and** `unavailable` with `cause: "fault"` for a fault the handler caught — is a **non-`isError`** structured result that increments a block-producer counter and publishes nothing; `isError: true` is left to the one thing the handler cannot decide, the MCP layer's own input-validation error on a call the handler never ran (D6). The flag matters because KPR-454's two capture points classify an `isError` result as a tool fault on both lanes: keeping it off every handler answer means an agent's typo, an operator's kill switch and a faulting ops-log read all mint no `hive-runtime:tool-failed`. The caught fault is instead the block producer's own *logged and counted* fact — its `faults` counter plus one warn line — which is exactly what KPR-458 D10(a) prescribes for a publish or read failure on the ops path ("logged and counted, never published", canon C14); routing it into the runtime producer's tool-health rows would be the ops path publishing about itself through another producer's door. The agent is still told the truth: `state` says the call did not take effect, `cause` says why (D2, D9). `agent_events`, `team_messages`, `agent_callbacks` are never written; `system:task_blocked`, `EVENT_SCHEMAS`, `Scheduler.checkEvents` and the `subscribe` field are untouched, exactly as KPR-454 D11 left them (D2, D9, D10).
- **In scope:** the two tools, the three rows, the accept-only job kind and a bounded `flush`, the log-side open-condition read, the KPR-455 arm 1 interface constants, tests, `CLAUDE.md`. **Out of scope:** any subscription, cadence, recipient or prompt rollout (KPR-458 D11 column 3); any reader, view, CLI or doctor section (KPR-455); any change to the coordination bus; any `hive.yaml` key; any notification to the blocked-on party; an `escalate` primitive (an escalation ladder is a re-publishing subscriber, KPR-458 canon).
- **⚠ Delegated, non-blocking, named in Assumptions:** the reason classes above; the `agent-work` subject and its fallback; the `blockedOn` vocabulary and the optional `blockedOnAgentId` (a fact about the condition — the outstanding act — never an owner field); the three-shape `rulingRef` grammar; the optional explicit `threadId` on `clear_block`; the bounded pre-read `flush`; the types-only declared shape with handler-side value rules and the non-`isError` handler answers (caught faults included); that cron-run blocks age to `unknown` rather than being cleared across runs. **⚠ Flagged for the merge coherence verdict:** the thread key refines the signed Gate 1 package line "work uses `(agent, workItemId)`" within that line's own caveat and under KPR-453 canon; the design owes no change under either reading, and the record-only supersession row is pre-drafted in Assumptions should the verdict hold a GATE1_AMENDMENT.

## Problem

Gate 1's consensus: "*Runtime emits, agents don't* … Agents tag only what the runtime can't see: coordination blocks and semantic blocks." KPR-454 shipped the runtime half. Today an agent that is blocked has exactly two outlets: narrate it in prose into whatever channel it is in (the noise this epic exists to remove), or `emit_event("system:task_blocked", …)` — which writes free text into a collection whose only reader spawns turns, and which no operational reader can query as a condition. Consequently KPR-455's work-status view (arm 1) has no producer: the reader is "correct today and returns only tool conditions". The stalled-work half of the epic's Storage section — "Work status keyed (agent, workItemId) — blocked until a same-run resumed / cancelled / escalated" — has no fact to derive from.

## Goals and non-goals

**Goals.** Let an agent state, as a published `ops_events` fact in the D2 envelope, that its work on a thread is blocked on another party or on a decision, and later that the block closed. Key the condition on the agent's work unit so it can be cleared from a later turn and after a restart. Reuse KPR-454's accept path, drainer, registry mechanics and bounds unchanged. Preserve worker containment, the three auto-injection gates and Lane B parity by inheritance. Make the fact honest with zero subscribers: recorded, not delivered. Give KPR-455 a stated interface for arm 1.

**Non-goals.** Notifying the blocked-on party (that is `team.send_message` / the coordination bus, unchanged). Any ledger row, delivery, nudge, snooze, intake or clearing *application* (KPR-468). Any reader, view, CLI, doctor section or the inbound acknowledgement edge (KPR-455). Any subscription row, transport binding, cadence, staleness horizon or retention value (operator, KPR-458 D11 column 3). Any change to `agent_events`, `EVENT_SCHEMAS`, `system:task_blocked`, `Scheduler.checkEvents` or the `subscribe` field. An owner, assignee, escalation target, severity or urgency on the event. An `escalate` tool. A publisher heartbeat or `ops_publisher_stats` (the KPR-455 request stands with the epic driver, unchanged). Any prompt, constitution or seed edit (no prompt rollout). Any `hive.yaml` key. Runtime-derived block detection (a block is an agent's statement; the runtime infers none).

## Design

### D1. Producer identity, and what is reused unchanged

`producer: "hive-agent"` — the agent's own statement about its own work, published by the engine on the agent's behalf through the tool. It is a bounded token under `OPS_TOKEN_RE`, not an enum member; the literal appears only in this producer's own rows and tool code, never in a validator (KPR-454 AC16).

### D2. The surface: two tools on the existing `event-bus` in-process server

**Decision.** `report_block` and `clear_block` are appended, as ordinary SDK `tool()` descriptors, to the array `buildEventBusTools(deps)` returns, built by a new `buildBlockTools(deps)` in `src/ops/block-producer.ts` from the same `EventBusToolDeps` (`db`, constructor `agentId`, `workItemContext` ref). `createEventBusMcpServer` is byte-unchanged; the `server.instance.registerTool` route the `schedule` server takes for strict objects is deliberately **not** used — D6 states why, and the consequence for the declared shape (types and optionality only; every value rule in the handler). No new MCP server. No new key in `IN_PROCESS_PORTED_SERVERS`, `WORKER_SERVER_DENYLIST`, `TURN_CONTEXT_DEPENDENT_SERVERS`, or the runner's three gates.

`event-bus` wins on every row but one (reach is opt-in per agent), and that one is the correct posture: an operator who removed `event-bus` from an agent removed its coordination surface and gets no block tools either; adding it back is the existing lever. A new server would be a strictly larger change for the same tools, and `schedule` would put block semantics on the wrong server to buy a reach the baseline already provides.

**Containment is asserted on the built set, per `CLAUDE.md`.** A worker-mode runner (`suppressAutoInjectedServers: true`, `coreServers` filtered by the denylist) builds a server set that does not contain `event-bus`, therefore no `report_block`/`clear_block`; the test drives `buildInProcessServers` + `buildToolTransportInventory` on such a runner and asserts absence there, never on the config array alone (AC1).

**Lane B parity by inheritance.** `buildToolTransportInventory` already emits an `event-bus` descriptor (`sdk-in-process`, `requires-hive-bridge`); `partitionInventoryForProvider` bridges it; the ToolBridge executes the same SDK server instance `buildInProcessServers(context)` returned, so the tools read the same live `workItemContext.current` on both lanes (KPR-453 canon). The plan drives one Lane B case through `buildLaneBHarness` (AC1).

**Tool response shape, and the `isError` boundary.** JSON text in the `schedule` shape, `{ state, ... }`, with one deliberate departure from that precedent: **the handler never sets `isError`.** Every answer it returns — `queued`, `no-open-block`, `refused` (+ `reason`), `disabled`, `unavailable` with `cause: "publisher-unset"` (the boot window), and `unavailable` with `cause: "fault"` when its own try/catch ran — is returned with `isError` absent. The only `isError: true` a caller of either tool can ever see is minted by the MCP layer before the handler runs, on a call the handler never saw (D6's residual). Two reasons, one per half. *The decided states:* KPR-454's shipped capture points classify an `isError` result as a tool fault on both lanes — Lane B `discover()` throws on it precisely so `wrap()`'s catch records it (`tool-bridge.ts:309-318`), and the Claude-lane `PostToolUseFailure` hook fires on it (probe class 2) with no per-tool exclusion (`agent-runner.ts:2031-2096`) — so under the precedent's flag D13's kill switch would mint a `hive-runtime:tool-failed` on `mcp__event-bus__report_block` per agent call, the very "spend the counter on an operator's deliberate lever" outcome D13 argues against, and every agent typo would become a tool-health fact. *The caught fault:* what the catch can catch in production is a rejecting `findOpenCondition` read — an `OpsPublisher` method faulting against the ops log (`enqueuePublish` is a synchronous push that cannot throw, and an insert rejection lands in the drainer after the tool has answered — Verified facts, D8). KPR-458 D10(a) fixes what the ops path does with its own publish or read failure: "logged and counted, never published" (`kpr-458-design.md:354`, canon C14). An `isError` here would hand that failure to the runtime producer's capture points and publish it as a `hive-runtime:tool-failed` — the ops path publishing about itself through a different producer's rows. So the caught fault answers `{ state: "unavailable", cause: "fault" }` non-`isError`, the block producer's `faults` counter advances, and one warn line names the tool and `String(err)` — that counter and line **are** the D10(a) record. The agent is still told the truth (the state says the call did not take effect, the cause says why) and its remedy is a transient's: retry on its next turn. The `schedule` tools predate those capture points; their `isError` on `unavailable` is theirs to revisit, not this child's.

**What KPR-454 records about each answer, both lanes — stated, not inferred:**

| Answer | `isError` | Claude lane (`PostToolUse*` hooks) | Lane B (`wrap()` in `tool-bridge.ts`) | Recorded by the runtime producer |
| --- | --- | --- | --- | --- |
| `queued`, `no-open-block`, `refused`, `disabled`, and `unavailable` with `cause: "fault"` (handler catch) | absent | `PostToolUse` → `observeToolSuccess` | success branch → `observeToolSuccess` | **no `tool-failed`**; a `tool-recovered` only if that tool's family already holds an open fault entry (`enqueueRecoveryIfOpen`, `publisher.ts:519-523`) — true, since the tool answered (a caught ops-log fault is the block producer's counted fact, not a tool-health fact); harmless |
| `unavailable`, `cause: "publisher-unset"` | absent | as above, but the singleton is unset, so `observeToolSuccess` returns at its first line | same | nothing at all |
| MCP-layer `Input validation error` (D6's residual: missing required key, non-string value) | `true`, minted by the SDK, not the handler | `PostToolUseFailure` → `observeToolFailure` | `discover()` throw → catch → `observeToolFailure` | one `hive-runtime:tool-failed` on `subject { kind: "tool", id: "mcp__event-bus__<tool>" }`, exactly as for every tool in the fleet; not preventable at the handler, minimised by D6's permissive shape; closed by the next non-`isError` answer |

Handlers never throw — every path is inside the try/catch every in-process tool carries (`CLAUDE.md`, KPR-122); the catch answers non-`isError` as above, counts `faults`, and warns with the tool name and `String(err)` — never the error object into any stored field. The `report_block` description says in its own words that the tool **records** a fact and **notifies nobody** — to alert the agent it is waiting on it uses `send_message` (team) as today — and that the agent clears the block itself with `clear_block` when it resumes or cancels. That description is the whole of the agent-facing guidance this child ships (no prompt rollout; "fix tool descriptions, not prompts").

### D3. The reason rows — three, shipped as one self-contained table

`src/ops/block-reasons.ts` (imports only `types.ts`/`ids.ts`, the `reasons.ts` layering), exporting `HIVE_AGENT_PRODUCER = "hive-agent"`, the three reason ids, and `HIVE_AGENT_REASONS` **in this order**:

| # | `reasonId` | `class` | `retry` | `clearsReasonIds` | `detailKeys` (all strings unless noted; `?` = optional) | `remediationTemplate` |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `block-cleared` | `informational` | `transient` | `["coordination-block", "semantic-block"]` | `agentId` (≤200), `outcome` (≤16: `resumed`\|`cancelled`), `workItemId?` (≤200), `threadId?` (≤200) | `"none; recorded so {agentId}'s block closes ({outcome}) and reopens as a new epoch if it returns"` |
| 2 | `coordination-block` | `resource` | `deterministic` | — | `agentId` (≤200), `blockedOn` (≤16: `agent`\|`human`\|`external`), `blockedOnAgentId?` (≤64), `workItemId?` (≤200), `threadId?` (≤200) | `"{agentId} is blocked on {blockedOn}; supply what it is waiting for, and it clears the block itself (clear_block, resumed or cancelled)"` |
| 3 | `semantic-block` | `judgment` | `deterministic` | — | `agentId` (≤200), `workItemId?` (≤200), `threadId?` (≤200) | `"{agentId} needs a ruling above its authority; a named human rules, and the agent clears the block citing the ruling"` |

Templates interpolate always-present keys only (the KPR-454 rule). `enabled: true` on all three at deploy. `agentId` is bounded at the 200 ceiling rather than KPR-454's optional `agentId ≤64` because here it is **required** and engine-held: agent ids are not length-validated anywhere (the admin tool describes "lowercase with hyphens" only), and a required key composed from an engine value must never trip the accept path's reject-and-count for every publish of one agent. `blockedOnAgentId` stays at 64 — it is agent-authored, so a refusal there is the agent's to fix.

**Classes, argued.** D3's table decides class by *who can clear it, by what act*. A coordination block is cleared when the awaited act lands and the agent resumes (or cancels) — the same producer asserting the recorded predicate now holds, which is `resource`. A semantic block is "a decision above the producer's authority", cleared only by a named human's ruling — `judgment`. KPR-458's example table put `coordination-block` under `judgment` with the template "rule on {question}…"; that table is labelled illustrative and its template would store prose (`{question}`) that C13 forbids, so it is not followed. ⚠ Delegated. Consequences that follow from the classes and are wanted: `coordination-block` is enable-gated on a clearing reason (row 1 provides it) and any same-producer `block-cleared` clears it at the ledger; `semantic-block` clears only with evidence (D7); neither is `integrity`, so both are dismissible.

**`retry: deterministic` on both.** Re-running the blocked agent does not unblock it; the other party's act or the ruling must land first. D3: "something must change first". Nudge cadence is `f(class, retry)` operator data and reads nothing here. ⚠ Delegated.

**Registration.** `reasons.ts` gains `OPS_REASON_TABLES = [HIVE_RUNTIME_REASONS, HIVE_AGENT_REASONS] as const`. The constructor asserts each table with `assertReasonTableLegal` (the gate is per-table; the `hive-agent` table is self-contained — row 1 names rows 2 and 3, row 2 is the only `resource` row and row 1 clears it); `init()` upserts each table in list order, each table's internal order preserved. **Clearing-first is load-bearing** for the same severity reason KPR-454 D5 argued: a fault between writes must never persist an enabled, unclearable `resource` row; a dangling forward reference is inert and the next boot repairs it. `enabled` stays `$setOnInsert` — the operator's kill switch survives upgrades. `auditLoadedEnableGate` is already generic over the loaded map and covers the new `resource` row with no change.

### D4. Subject, dedupe identity, and why the thread — not the turn — is the key

```
subject = { kind: "agent-work", id: "<agentId>:<threadId>" }        // the normal shape
        = { kind: "agent-work", id: "<agentId>" }                    // fallback (below)
family  = "hive-agent:agent-work:<subject.id>:<reasonId>"
dedupeKey = family + ":" + generation                                 // D2's formula, unchanged
```

`agentId` is the constructor slug (`deps.agentId`); `threadId` is `workItemContext.current.threadId` read at execution. Both are engine-held; neither is a parameter.

**Why not `workItemId`.** The epic's storage note keyed work status on `(agent, workItemId)` and, in the same breath, warned that "`workItemId` is turn identity, not proof of task continuity — a later callback/retry needs an explicit link to the blocked work." KPR-453 canon fixed that: identity "proves neither unique attempt nor task continuity". A Slack thread produces a new `WorkItem.id` per human message, so a block raised on message `t1` and cleared on the reply at `t3` would be two subjects and the clear would find nothing. The engine's own unit of continuing work is the **thread** — the per-thread lock key `agentId:threadId`, the session-resume key — so that is the explicit link. `workItemId` still identifies *the turn that raised or cleared the block*, and rides `detail` and `evidence` exactly as KPR-454 carries it.

**Authority for the key, named line by line.** The same `(agent, workItemId)` phrasing appears in two signed places, and this spec's position on each is stated rather than left for the merge verdict to discover:

- **The signed Gate 1 package** (KPR-451#comment-95cc0708, Key Points): "*Keep tool health and work status distinct.* Tool health uses `(tool, error signature)`; work uses `(agent, workItemId)`. Stale state becomes `unknown`, never implicitly healthy or resolved. A later retry/callback needs an explicit link to blocked work; owner/escalation targets require deliberate writes, and escalation does not resolve a block. Maturation must settle lifecycle evidence and timing against the human policy, without inventing thresholds." The key and its caveat are one bullet: the line itself says a later turn "needs an explicit link to blocked work" and delegates lifecycle evidence to maturation. This spec supplies that link — the thread — and keeps `(agent, workItemId)` on every event (`detail.agentId` + `detail.workItemId`, the work-item `evidence` ref) as the identity of the raising or clearing turn. Read together with KPR-453's binding canon bullet ("identity proves neither unique attempt nor task continuity" — ratified after Gate 1, and the Decision Register carries no `(agent, workItemId)` bullet of its own), a cross-turn condition key on `workItemId` alone is canon-incompatible; the package line is refined within its own caveat, not contradicted. **Position: no design amendment is owed.** Plainly flagged, though: this epic's coherence machinery has twice held a *record-only* GATE1_AMENDMENT for package text a ruled design outran (KPR-458's two lines; KPR-454's clause), so the merge verdict may read "work uses `(agent, workItemId)`" as a stated mechanism. If it does, the route is the append-only line-level row pre-drafted in Assumptions — a text correction; nothing in this design changes under either reading.
- **KPR-458 D8's signed body** (`kpr-458-design.md:328`): "*Work status*, keyed `subject` where `subject.kind = "workItem"`: open until a class-legal clearing fact." The view is keyed on **`subject`**; `workItem` is the kind D2's envelope row (`:103`) lists first among "the producer's own key space (`workItem`, `obligationOccurrence`, `capability`, `unit`, …)" — an open, producer-declared space, of which `agent-work` is this producer's member. KPR-455's own signed design already reads it that way ("generically over any `subject.kind`, not only `workItem`", `kpr-455-design.md:126`). No supersession note is owed on `kpr-458-design.md`; KPR-455's revision (already required by the reject ruling) is where the reader states the kind it consumes (D12).

**Why the agent is embedded.** Conference threads dispatch one trigger to several agents (KPR-386); two agents blocked on the same thread must be two conditions, and one agent's clear must not close the other's. A subject bound to the calling agent also means **an agent can only ever report or clear its own blocks** — the tool has no parameter naming another agent as the subject.

**Fallback and bounds.** `subject.id` is bounded at 200 (`OPS_ID_MAX_LENGTH`, reject-and-count at accept). The tool composes the id and checks, in order: the live ref holds a context at all (`workItemContext.current` is refreshed *including absence* — KPR-453 canon — so a stdio-placeholder or context-less construction reads `undefined`), `threadId` passes `ADMISSIBLE_ID_RE` (a `scheduler:<agent>:<multi word label>:<epoch>` thread does not — the deliberate `sched:` exclusion KPR-454 D6 made) **and** the composed id is ≤ 200. On any failure the subject falls back to `"<agentId>"` and the tool counts `subjectFallback`. The fallback collapses every block that agent reports without a storable thread into one condition — the same accepted-collapse shape as KPR-454's one-condition-per-tool, and confined to turns that have no storable work unit. ⚠ Delegated.

**Named residual — cron-run blocks.** A scheduled turn's thread is per run (`scheduler:<agentId>:<task>:<epoch>`): when admissible, a block raised in one run keys a subject no later run will compose, so `clear_block` in the next run answers `no-open-block` and the condition ages into the reader's `unknown` past its horizon. That is the honest reading for a fact nobody re-asserted, and it is the behaviour Gate 1 asked for ("defaults to unknown after N minutes rather than trusting self-reported 'resolved'"). The explicit `threadId` parameter on `clear_block` (D7) is the manual escape. ⚠ Named, not solved; a per-job stable thread for cron is a scheduler question outside this child.

**Generation rule, declared per KPR-458 D2 in the same terms as `hive-runtime`'s.** `generation` is `0` on the first block report for a family and advances by exactly one when a block is reported for that family again **after** a `block-cleared` naming that family has been published; never on repetition, elapsed time, retry, or an unanswered nudge. The accept path already implements exactly this for any producer (`resolveGeneration`: latest condition vs latest `clearsFamily` under the compound order), so the declaration is a statement of what the shared path does, pinned by AC7 rather than re-implemented. On a resolver read fault the fallback reads the open-condition map, which holds no `hive-agent` entry (D8), so the publish proceeds at `0` — D2's named bounded mis-attachment, never a lost fact.

### D5. `waiting` — derived from the one prefix table, never a parameter

`waiting = waitingFor(workItemContext.current?.workItemId)` — the **unfiltered** id, exactly as `observe.ts:100` does; absent ⇒ `nobody`. A block raised in a human's live Slack thread is `human-now` (additive — the human sees the agent's own words in-thread; no engine subscription selects it, KPR-458 D10); in a `team-` turn it is `agent`; in a cron, callback, event or worker turn it is `nobody`; `obligation` is never produced here (canon). No second prefix predicate is introduced; `single-prefix-predicate.test.ts` stays green with no allowlist change (AC4).

The agent does not get to set `waiting`. That is the same structural refusal as registry-declared `class`/`retry`: a self-declared axis converges on its maximum (the Florist `loudness` lesson), and the invocation context is a fact the runtime already holds.

`block-cleared` publishes a **fixed** `waiting: "nobody"`, the KPR-454 `tool-recovered` posture: a clearing fact blocks no one, and a derived value would let a `human-now` subscription select clears.

### D6. Parameters, `detail`, `evidence` — redaction is the schema, value rules live in the handler, and the tool refuses before the accept path can reject

**Where each check runs — the mechanism, verified at the tree.** `createSdkMcpServer` hands a `tool()` descriptor's raw shape to `McpServer.registerTool`, which wraps it as a **non-strict** `z.object(shape)`; the MCP `CallTool` handler parses the arguments against that object **before** the handler runs and answers a parse failure as `{ isError: true, content: [text: "Input validation error: …"] }` (`mcp.js:100-181`, Verified facts). Two consequences fix the design: (1) any enum, regex or cross-field rule written into the declared shape is enforced by the MCP layer — the handler never sees the call, so there is no `reason` code, no counter, and the answer is an `isError` result that KPR-454 records as a tool fault (D2); (2) unknown keys are stripped, never refused. The `schedule` server's `server.instance.registerTool` + `.strict()` route (`schedule-mcp-server.ts:282-299`) changes only (2) — a strict object refuses unknown keys, but still at the MCP layer as an `isError` — so it would buy a refusal at the price of a `tool-failed` per stray key and change D2's append/byte-unchanged claims for nothing the handler cannot do. **Therefore the declared shape carries the type and optionality of each key only** — `z.string()` / `z.string().optional()`, each with a `.describe()` naming the closed vocabulary or grammar so the JSON schema the model sees still says what is admitted — **and every value rule below is a handler check**, answered `{ state: "refused", reason: <code> }` (non-`isError`, D2) and counted on `refused`. What remains at the MCP layer is the irreducible type-level residual: a missing required key (`kind`, `outcome`) or a non-string value — an `isError` carrying the SDK's text, no `reason`, no block-producer counter, recorded by KPR-454 exactly as for every other tool in the fleet (Edge 20). ⚠ Delegated: the permissive shape; reversal (declaring the enums in the shape) is a one-line change per key that moves that key's refusals to the MCP layer and out of AC5/AC9's handler-visible set.

**`report_block` parameters** — the *declared* column is the raw shape handed to `tool()`; the *value rule* column is the handler's, with its `reason` code:

| param | declared | value rule (handler) → `reason` | required | becomes |
| --- | --- | --- | --- | --- |
| `kind` | `z.string()` | `"coordination" \| "semantic"` → `kind` | yes | `reasonId` (`coordination-block` / `semantic-block`) |
| `blockedOn` | `z.string().optional()` | `"agent" \| "human" \| "external"`; required with `coordination`, refused with `semantic` → `blocked-on` | coordination only | `detail.blockedOn` |
| `blockedOnAgentId` | `z.string().optional()` | `^[a-z][a-z0-9-]{0,63}$`; only with `blockedOn: "agent"` → `blocked-on-agent-id` | optional | `detail.blockedOnAgentId` |

**`clear_block` parameters:**

| param | declared | value rule (handler) → `reason` | required | becomes |
| --- | --- | --- | --- | --- |
| `kind` | `z.string()` | `"coordination" \| "semantic"` → `kind` | yes | selects the family |
| `outcome` | `z.string()` | `"resumed" \| "cancelled"` → `outcome` | yes | `detail.outcome` |
| `rulingRef` | `z.string().optional()` | `RULING_REF_RE` (below) → `ruling-ref-shape`; absent on `semantic` → `ruling-required` | **required for `semantic`**, optional for `coordination` | `evidence: [{ kind: "ruling", id }]` |
| `threadId` | `z.string().optional()` | `ADMISSIBLE_ID_RE` → `thread-id-shape` | optional | overrides the live thread when composing the family (the block was raised in another thread of the **same agent**) |

The seven `reason` codes (`kind`, `blocked-on`, `blocked-on-agent-id`, `outcome`, `ruling-ref-shape`, `ruling-required`, `thread-id-shape`) are module literals exported for the tests; every refusal names the admitted values in its text so the agent can fix the call. `z.string()` admits the empty string, so the seven codes are made total over the string domain by one rule: `""` is treated as **absent** for `rulingRef` only — a semantic clear with `rulingRef: ""` is `ruling-required`, a coordination clear with it simply carries no ruling evidence — and is an ordinary value refusal everywhere else (`kind`/`outcome`/`blockedOn` have no empty member ⇒ `kind`/`outcome`/`blocked-on`; the `blockedOnAgentId` and `threadId` patterns each require at least one character ⇒ `blocked-on-agent-id`/`thread-id-shape`).

**What a ruling reference is.** A ruling is given where humans rule — in a Slack thread or on a ticket — so `rulingRef` is one of three closed shapes, `RULING_REF_RE` (a module literal in `block-producer.ts`; every shape is ≤ 40 characters and `ADMISSIBLE_ID_RE`-admissible, so the accept path's `evidence-id-bounds` check (1..200, `publisher.ts:703`) never fires on an admitted value):

| shape | grammar | example |
| --- | --- | --- |
| Slack message / thread ts | `^\d{10}\.\d{6}$` | `1757900000.123456` |
| conversation-qualified ts | `^[CDG][A-Z0-9]{8,12}:\d{10}\.\d{6}$` | `C0AB12CD3EF:1757900000.123456` |
| issue key, optionally comment-anchored | `^[A-Z][A-Z0-9]{1,9}-\d{1,7}(?:#comment-[0-9a-f]{8})?$` | `KPR-451#comment-60079ae4` |

Nothing else is admitted: a credential-shaped string (`sk-ant-…`, a 32/40-hex secret, a JWT), a URL, a path or a sentence fails every shape and is `refused` with `reason: "ruling-ref-shape"` naming the three, so the agent can fix it — a handler check (the declared shape says only `string`), so it is counted and non-`isError`. A ruling received on a surface with no citable id — SMS, voice, in person — is cited by the Slack message or ticket comment that records it; the engine verifies **shape, never truth** (Assumptions). ⚠ Delegated: the three shapes; widening is a one-line regex change plus its AC5 limb.

**The `threadId` override cannot store a string the engine did not compose.** It participates only in composing the family that `findOpenCondition` looks up (D7 step 5); a value naming no open condition — a pasted token included — answers `no-open-block` and publishes nothing. The only way a family reaches the log is a `report_block` whose thread came from the live ref. Its own bound is `ADMISSIBLE_ID_RE` (a handler check, `thread-id-shape`) so that any engine-composed thread id is expressible; note that `ADMISSIBLE_ID_RE` is `/^[A-Za-z0-9_.:#+@-]{1,200}$/` (`ids.ts:121`) — letters, digits and `_ . : # + @ -` — so a credential-shaped token passes the shape rule and lands on `no-open-block` — the no-novel-string property, not the shape rule, is what keeps it out of the log (AC5).

Engine-held values composed into every publish: `detail.agentId` (constructor slug), `detail.workItemId` and `detail.threadId` (from the live ref, through `admissibleIdOrUndefined`, omitted on breach with `publisher.countIdOmitted()` — the capture-point posture, reused rather than re-invented), `evidence: [{ kind: "work-item", id: workItemId }]` when admissible, `[]` otherwise (`report_block`); for `clear_block`, `evidence` is the ruling reference when supplied plus the clearing turn's `work-item` when admissible, at most two entries (well under `OPS_EVIDENCE_MAX`). **On a clear, `detail.threadId` and `detail.workItemId` are always the clearing turn's own** — the live ref's — even when the `threadId` parameter overrides the family: `detail` records "the identity of the raising or clearing turn" (D4), and the cleared family's thread is recoverable from `clears`/`clearsFamily`. A reader that wants the blocked thread reads the key; one that wants where the clear was issued reads `detail` (D12; AC2).

**No free text, anywhere.** There is no `summary`, `question`, `description`, `note` or `label` parameter, and none may be added: KPR-458 D9/C13 forbids message text and free-form prose in any stored field, KPR-454 canon treats a multi-word cron label as prose to be omitted, and a per-agent diagnostics surface is exactly where a token gets pasted. What a responder needs is a reference to open — the thread and the work item — plus closed tokens saying what kind of block and on whom; the remediation template supplies the sentence. The two agent-authored references are bounded accordingly: `rulingRef` by the closed grammar above (the one stored value an agent types, so it gets the tightest bound), `threadId` by the no-novel-string property above. `blockedOnAgentId` is a bounded lowercase slug (the agent-id convention), not validated against the roster (a live roster read on the tool path buys nothing a reader cannot do later; ⚠ delegated), and it is **a fact about the condition** — the outstanding act's party — not an owner: no engine path reads it, subscriptions cannot filter on `detail`, and it is absent from the explicitly-absent list's meaning (`owner`, `assignee`, `escalatedTo` all name who *handles* the notification; this names who the agent is waiting on).

**Two validation layers, deliberately distinct, as in KPR-454 D6 — and the first is the handler, not the schema.** The handler **refuses** a malformed value with `{ state: "refused", reason }` (non-`isError`, D2) and increments its own `refused` counter — the agent sees why and can fix it; nothing is published, and nothing is recorded about the call by KPR-454. The accept path's registry-built detail schema still **rejects and counts** on breach — but for input the handler admitted it must never fire, or the two have drifted. AC5 drives the whole value matrix through the handler, asserts the publisher's `rejected` counter stays at zero, and asserts the declared shape's key set and per-key type/optionality literally, so no value rule can silently migrate into the shape and out of the handler-visible set (NV9). An `evidence` kind and `subject.kind` are literals in this module and satisfy `OPS_TOKEN_RE` by test (the KPR-454 `workItem`→`work-item` lesson).

### D7. The clearing fact — log-resolved, class-honest, never blind

`clear_block(kind, outcome, rulingRef?, threadId?)`:

Every answer below, the caught fault included, is non-`isError` (D2). The whole body sits in the handler's try/catch; anything that throws or rejects out of steps 4–7 lands in the catch, which answers `{ state: "unavailable", cause: "fault" }` (no `isError`), counts `faults` and warns once — the KPR-458 D10(a) record. In production the only rejecter is step 5's read: step 4's `flush` never throws, step 7's `enqueuePublish` is a synchronous push that cannot throw, and the insert it queues runs in the drainer after step 8 has answered (Verified facts; D8). A throwing `enqueuePublish` is a test double for the C15 limb (AC11).

1. **Availability.** No publisher singleton ⇒ `{ state: "unavailable", cause: "publisher-unset" }`. Then `isReasonEnabled("hive-agent", "block-cleared")` — the row **this tool publishes**, not the condition row — `false` ⇒ `{ state: "disabled" }`. A clear of an already-open block therefore **proceeds even when `coordination-block`/`semantic-block` has since been disabled**: the accept path's step 1 tests only the publishing reason's row and its step 4 `clears` legality reads the publishing row's `clearsReasonIds`, never the cleared row's `enabled` (`publisher.ts:688-689`, `:736-748`), so the operator's lever on the condition rows stops new blocks without stranding open ones and never spends `unknown-or-disabled-reason` on itself (D13; AC10).
2. **Parameter and class rules — handler checks, no I/O.** `kind` and `outcome` against their enums, `rulingRef` against `RULING_REF_RE`, `threadId` against `ADMISSIBLE_ID_RE` (D6's table, each with its `reason` code), and the one class rule: for `kind: "semantic"` a missing `rulingRef` ⇒ `{ state: "refused", reason: "ruling-required" }`, no publish. This step runs **before the flush and the two reads**, so a ref-less semantic clear never pays I/O — and, by that order, when nothing is open *and* no ref is supplied, **`refused` wins** (Edge 8); `no-open-block` is only ever answered to a well-formed call. **Why the class rule is the tool's — primary reason:** the cleared row's class is `judgment`, and KPR-458 D3/D8 says a `judgment` condition "accepts only an event recording a named human ruling" — so a `hive-agent` semantic clear must *cite* one, and the tool is the only place that can insist on the citation. **Secondary, and not the load-bearing reason:** KPR-468's `clearingProvenanceOk` (`ingest.ts:105-107`) and KPR-455's reader (its D5) apply a `judgment` clear only with `evidence.length >= 1`; that floor is met by *any* evidence entry, and D6 puts the clearing turn's own `work-item` reference into `evidence` on every admissible turn — so on a Slack-ts turn a no-ruling clear would pass ingest and the view without any ruling at all. The floor is therefore not what makes the requirement hold; the tool's refusal is. Where the floor *does* bite — a clearing turn with no admissible work item (cron, ws/voice), so `evidence` would be `[]` — a no-ruling clear would be *stored but inert* at the ledger and the view while the class-blind epoch resolver (step 5) still counted it as the more recent fact and advanced the next report's `generation`, minting a fresh ledger row beside the still-open one; the refusal closes that case too. Net: every `hive-agent` clearing fact is class-legal by construction because the tool refuses, and the ledger/view floor is a backstop that the ruling reference always satisfies. (A hand-inserted document is outside this guarantee, as it is outside KPR-454's.)
3. **Compose the family** from the constructor agent id and the live (or overridden) thread id under D4's rules.
4. **Flush, bounded.** `await publisher.flush(FLUSH_DEADLINE_MS)` — the `__drainForTests` loop with a deadline (⚠ value delegated; small, on the order of a second). This makes a block reported earlier *in the same turn* visible to the read below; a deadline that elapses (a failure storm has the queue deep) does not fail the call and never throws — the read proceeds and the response carries `queueIdle: false` so a `no-open-block` under that condition is honestly qualified.
5. **Resolve the open condition from the log**, not from the open-condition map: `publisher.findOpenCondition({ producer, subject, reasonId })` — the family's components, D1 — performs the resolver's two indexed reads — latest event in the family under the condition `reasonId`, latest event whose `clearsFamily` equals the family — and returns the condition's `dedupeKey` iff a condition exists and no clearing fact is more recent under `(publishedAt, _id)`. It applies **no class-legality test** — deliberately the same rule as `resolveGeneration`, so the key a clear names is always the key the next report's `generation` would be computed against; for `hive-agent` events the ledger's and the view's class-legal reading agrees with it by step 2. The plan factors the two reads and the comparison into **one private helper** that both `resolveGeneration` and `findOpenCondition` call, so the two "latest condition vs latest clearing" comparisons cannot drift. Unlike `resolveGeneration`, `findOpenCondition` has **no fallback**: a read fault rejects out to the handler's catch ⇒ `{ state: "unavailable", cause: "fault" }`, non-`isError`, `faults` +1, one warn line — the tool **never publishes a clear it could not verify** (D2: a clearing fact for a condition never raised is noise), and the fault is logged and counted by this producer, never published by any (KPR-458 D10(a); Edge 24). **This is the one place this producer deliberately differs from `hive-runtime`**: KPR-454 resolves openness from the in-process map because a tool success is the hot path and a per-success read was rejected against C15; a block clear is a rare, deliberate agent act on its own turn, and a block is long-lived across deploys, so the restart residual KPR-454 accepted ("one lost epoch boundary per restart per open condition") would here mean *a block raised before a restart can never be cleared* — unacceptable for the fact this producer exists to record. The log is the source of truth; AC7 pins a clear across a simulated restart.
6. **No open condition** ⇒ `{ state: "no-open-block", queueIdle }`, no publish, counted `clearNoOpen`.
7. **Publish** `block-cleared` with `clears: <that dedupeKey>`, `waiting: "nobody"`, `detail: { agentId, outcome, workItemId?, threadId? }` — `workItemId`/`threadId` are the **clearing turn's**, from the live ref, regardless of any `threadId` override on the family (D6) — `evidence` per D6, through `enqueuePublish` (D8). The accept path validates C19 (`block-cleared` declares both condition reasons), `clears-producer` (own family) and derives `clearsFamily`; `generation` is `0` (a clearing publish skips the resolver), so every clear for one family renews one informational `…:block-cleared:0` row at the ledger — the `tool-recovered` shape.
8. Respond `{ state: "queued", clears, outcome, queueIdle }`.

`report_block` has the same skeleton without steps 4–6 (no flush, no read, no `no-open-block`): availability (its `isReasonEnabled` reads the row it publishes — `coordination-block` or `semantic-block` by `kind`), parameter rules, compose, publish through `enqueuePublish`, respond `{ state: "queued", kind }`; the same catch (reachable there only by a test double — no read, and `enqueuePublish` cannot throw), the same non-`isError` posture.

An `escalated` outcome does **not** exist: escalation changes who handles a block and does not resolve it (Gate 1), and an escalation ladder is a re-publishing subscriber, not a primitive (KPR-458 canon). An agent that escalates does so with `send_message` and leaves the block open.

`report_block` on an already-open family is a renewal (same `dedupeKey`, `generation` unchanged, D7 rule 4 at the ledger, C18) — an agent may re-assert a block on every turn it remains blocked at no cost beyond one appended log row. Read the count correctly: under `retry: deterministic` KPR-458 D7 rule 4's "renewing repeatedly with no clearing fact is a countable defect signal in the responder" means the **awaited party** has not acted — the renewal count measures the block's age in turns, never a defect in the reporting agent.

### D8. Ordering — every publish rides the one serial drainer

KPR-468 canon binds this child by name: preserve the shared publish/drain ordering the notifier cursor consumes. The mechanism that ordering rests on is that the **single serial drainer** stamps `publishedAt` and mints `_id` (client-side, per-process counter) and awaits the insert before touching the next job, so insertion completion order is stamp order. A synchronous accept from the tool path — running concurrently with the drainer — would break that: tool publish `A` stamps `t1`, drainer job `B` stamps `t2 > t1` and lands, the sweep advances its cursor past `(t2, id_B)`, then `A` lands at `(t1, id_A)` **behind** the watermark and is never ingested (`strictlyAfter`, `ingest.ts:56-62`). Nothing downstream can repair that; the event would be recorded and never notified.

**Therefore:** both tools enqueue and return; neither awaits acceptance; nothing in `src/ops/block-*.ts` touches an `ops_events` collection handle. `OpsPublisher` gains a third job kind — `{ kind: "publish"; input }` via `enqueuePublish(input)` — whose `runJob` arm is `await this.accept(job.input)` and **nothing else**: no open-condition entry is created (that map is `hive-runtime`'s recovery bookkeeping; a block entry there would consume slots of a cap sized for tools and evict a live tool condition, and nothing would ever read it), and no entry is removed. The existing `failure`/`recovery` arms are untouched. The same queue-depth, drop-oldest, `stopping` and shutdown-drain rules apply, so a block report enqueued at the edge of an overflow can be dropped and counted (`queueOverflow`) after the tool answered `queued`, and a job whose insert rejects inside the drainer is counted (`publishFaults`) and warned — never stored, never published about, no `hive-runtime` document either, since the tool's answer was non-`isError` — the same residuals the capture points carry, named rather than papered over (Edge 13, AC11); the agent's next turn can re-assert (a renewal is free). The tool cannot see either outcome: by the time the drainer runs the job the handler has returned.

A repository guard test (`src/ops/single-events-writer.test.ts`, the `single-prefix-predicate.test.ts` shape) pins that, outside `*.test.ts` **and outside `src/ops/testing/**`** (the KPR-454 AC7/AC15 test-double precedent — at `2b33b83a` `notifier-harness.ts:28,276` imports the constant and inserts into the collection directly, and `lane-harness.ts:34,70` reads it; both are plain modules, so a guard without this exclusion is red on day one), `OPS_EVENTS_COLLECTION` is referenced only by `types.ts` and `store.ts`, the literal `"ops_events"` only by `types.ts`, and `store.events.insertOne(` only by `publisher.ts` — keyed on the `OpsStore` handle, not the bare `.events.insertOne(`, which also matches `src/workflow/event-emitter.ts:65`'s unrelated collection; comment lines are stripped before matching, since `types.ts:48`'s doc comment quotes the call. A future writer must go through the drainer or argue with that test. Reads are unconstrained (KPR-455 will read; it adds itself to the constant's allowlist when it lands).

The block producer adds **no loader**: it holds no subscription set, no reason map, no timer, and calls neither `loadSubscriptions` nor `reloadSubscriptions` (KPR-507 canon; AC8).

### D9. The ops path publishes nothing about itself, and nothing here spawns a turn

Every fault on the tool path — publisher unset, reason disabled, parameter refused, no open block, a caught read fault, flush deadline — is answered to the agent as a structured **non-`isError`** tool result and counted on the block producer's own counters (`reported`, `cleared`, `clearNoOpen`, `refused`, `unavailable`, `faults`, `subjectFallback`; behind an uncalled `getBlockProducerSnapshot()`, the KPR-454 `getSnapshot()` posture); the caught fault also warns once per occurrence with the tool name and `String(err)`. The counters are **module-global** in `block-producer.ts` — one set per process, the `getSnapshot()` posture — not per runner: the tools are built once per runner and a per-runner counter would die with the spawn, so a fleet-wide `refused` count would never be readable. **None is published — by this producer or by any other:** no `hive-agent` document ever describes a failed `report_block` or `clear_block`, and because every handler answer is non-`isError` (D2), the runtime producer's capture points see each as a successful call on both lanes — no `hive-runtime:tool-failed`, at most a true `tool-recovered` if that tool already held an open fault condition (the capture points' own semantics, not this producer's). That is KPR-458 D10(a) applied literally: a publish or read failure on the ops path is *logged and counted, never published* — the `faults` counter and its warn line are the record for a rejecting ops-log read, and `publishFaults` with its existing line (`publisher.ts:584-591`) is the record for an insert that rejects in the drainer after the tool answered `queued` (D8). The one `isError` a caller can see is the MCP layer's input-validation error on a call the handler never ran (D6); KPR-454 records it as one `hive-runtime:tool-failed` on `subject { kind: "tool", id: "mcp__event-bus__report_block" | "mcp__event-bus__clear_block" }` — a fact about the tool contract, published by the runtime producer under its own rows exactly as for any tool, and not a fault of the ops path. Publisher-side faults keep their existing counters (`rejected`, `publishFaults`, `queueOverflow`, `idOmitted`).

Neither tool writes `agent_events`, `team_messages`, `team_pending_requests` or `agent_callbacks`, calls `emit_event`, or reaches any `runWorkItemTurn`/`spawnTurn` path. A block report's *only* effect is one appended `ops_events` row (and, once an operator subscribes, whatever KPR-468 does with it on its own sweep). Gate 1's "another agent waiting → notify that agent internally" is served by `team.send_message`, unchanged and deliberately not bundled: bundling would make a store-only record spawn a turn (D10 invariant (b)) and would make the record's honesty depend on a delivery.

C15 holds as it does for the capture points: the handlers are wrapped, a throwing publisher or a rejecting ops-log read yields `{ state: "unavailable", cause: "fault" }` without `isError`, a rejecting insert is the drainer's `publishFaults` after a `queued` answer, and the agent's turn continues with its `RunResult` classification unchanged (AC11).

### D10. Relation to `agent_events`, `system:task_blocked`, and `Scheduler.checkEvents` — untouched

Nothing in `src/events/event-types.ts`, `emit_event`, `src/scheduler/scheduler.ts` or the `subscribe` agent-definition field changes. `system:task_blocked` remains what it is: a **coordination-bus message** whose publication fans out `deliveries[]` and whose only reader spawns turns for `system`-domain subscribers. `report_block` is an **operational record** that spawns nothing. They coexist and neither bridges to the other: an automatic "every `system:task_blocked` also publishes a `coordination-block`" would derive an agent's semantic statement from a free-text payload the ops contract cannot store, and would couple the record's existence to a turn-spawning write — the shape KPR-458 D10 declines. The only cross-reference is prose in `report_block`'s description (D2). Deprecating `system:task_blocked` is not this child's call and is not proposed.

### D11. Work identity and ownership — the KPR-453 shape, and no owner anywhere

`agentId` is `deps.agentId`, constructor-stable on the runner (the `schedule`/KPR-456 pattern). `workItemId` and `threadId` are read from `deps.workItemContext.current` **at execution**, never captured at build time (the server is cached across turns; the ref is refreshed by `buildInProcessServers(context)` on both lanes, including absence). No parameter lets the agent name a work item, a thread it did not run in (the `clear_block` override names a thread of the *same* agent), or another agent as the subject. Retries and outage replay may reuse a `WorkItem.id`; a replayed turn re-issuing `report_block` renews the same family, which is correct.

**Delegate subagents inherit the tools under the parent's slug — stated, not new.** Claude-lane delegate definitions (`agent-runner.ts:1886`) carry no `tools` allowlist, so an SDK subagent inherits the parent session's MCP tools and can call `report_block`/`clear_block`; the constructor `agentId` is the parent's, so the block is the parent's block on the parent's thread — exactly as `emit_event` and `team` behave for delegates today, and the KPR-454 canon shape (nested delegates carry the parent's slug, a delegate's identity is never stored). No new exposure class opens; the containment story is complete because the worker/scribe boundary (D2) is where the tools are absent, and the delegate boundary is where they were already reachable.

No `owner`, `assignee`, `escalatedTo`, `severity` or urgency exists on any event or parameter, and none may be added (KPR-458 D2, canon). Ownership of a block's *notification* is a subscription row; every acknowledgement is an attributed ledger act (KPR-468). The Gate 1 phrase "owner/escalation targets require deliberate writes" is met under the contract's stronger mechanism: the deliberate write is a subscription registration, and the deliberate act is an attributed acknowledgement — never a field on the fact.

## Edge cases

1. **Publisher unset** (boot window, or `init()` faulted and left it unset): both tools return `unavailable` (`cause: "publisher-unset"`, non-`isError`); no throw, no write; KPR-454 records nothing either — its `observe*` calls return on the same unset singleton.
2. **Reason disabled by the operator**: `disabled` (non-`isError`); nothing enqueued; `rejected` unchanged; no `tool-failed`. `clear_block` is gated on `block-cleared`, so an open block is still clearable (D7 step 1).
3. **Thread id inadmissible or composed subject > 200**: agent-level fallback subject, `subjectFallback` counted, `detail.threadId` omitted, `idOmitted` counted.
4. **Work-item id inadmissible** (client-supplied ws/voice id, multi-word cron label): `detail.workItemId` omitted, `evidence` lacks the `work-item` ref, `waiting` still derived from the unfiltered id.
5. **Repeated `report_block`** on an open family: one more log row, same `dedupeKey`, `generation` unchanged (C18).
6. **report → clear → report**: the third publish carries `generation + 1` and a fresh `dedupeKey`.
7. **`clear_block` with nothing open**: `no-open-block` (non-`isError`), no publish.
8. **`clear_block(kind: "semantic")` without `rulingRef`**: `refused` (`ruling-required`, non-`isError`), no publish — decided at D7 step 2 before any I/O, so it wins over `no-open-block` when nothing is open either.
9. **Report and clear in one turn**: `flush` makes the report visible; the clear lands after it in FIFO order. If the flush deadline elapses under a storm the response says `queueIdle: false`; a `no-open-block` there is a qualified answer, and the agent may retry on its next turn.
10. **Two agents on one thread** (conference): two subjects, two families; one agent's clear never touches the other's.
11. **Contained worker or scribe**: no `event-bus` in the built server set, so no tools; the runtime still publishes *about* them via KPR-454. No outbound surface opens.
12. **Lane B agent**: tools are bridged and execute against the same live context; identical stored shape (AC1, AC2).
13. **Queue overflow, shutdown, or a rejecting insert after `queued`**: the job may be dropped oldest-first (`queueOverflow`), refused by the `stopping` latch (`drainDropped`), or fail its insert inside the drainer (`publishFaults`, one warn line) — counted, never stored, never published about, and invisible to the tool, which had already answered; the agent's next renewal repairs it. Same residual as the capture points (AC11 limb iii).
14. **Restart between report and clear**: the clear resolves the open block from the log and succeeds — the property D7 exists for.
15. **`human-now` block**: recorded, additive; the human already sees the agent's own words in the thread; no engine subscription selects it.
16. **Cron-run block**: keys a per-run subject; not cleared by the next run (`no-open-block`); ages to `unknown` in the reader; explicit `threadId` on `clear_block` is the manual escape (D4 residual).
17. **`clear_block` with an explicit `threadId`** of a family with no open condition: `no-open-block`; it can never name another agent's family because the agent id is composed in. Of a family **with** an open condition: the clear's `clears`/`clearsFamily` name that family while `detail.threadId`/`detail.workItemId` are the clearing turn's own (D6).
18. **`blockedOnAgentId` naming a non-existent agent**: stored as a bounded slug; not validated against the roster; a reader that wants to resolve it can (⚠).
19. **Epoch resolver read fault** during a block report: publish proceeds at the map fallback, which is `0` for this producer (no map entry) — D2's bounded mis-attachment, never a lost fact; `epochResolveFaults` counts it.
20. **Agent supplies extra/unknown parameters**: the MCP layer's non-strict `z.object(shape)` **strips** them before the handler runs — no refusal, no counter, nothing reaches the accept path, and the call proceeds on its declared keys. A **wrong-typed** or **missing required** key (`kind: 42`, no `outcome`) is the MCP layer's `InvalidParams` — an `isError` result carrying the SDK's `Input validation error` text, no `reason`, no block-producer counter, and one `hive-runtime:tool-failed` from KPR-454 as for any tool. A wrong **value** on a declared key (`kind: "waiting"`) is the handler's `refused` with a coded `reason` (D6).
21. **Live ref holds no context** (`workItemContext.current === undefined` — a construction path with no `WorkItem`, refreshed as absence per KPR-453): no thread and no work item ⇒ fallback subject `"<agentId>"`, `subjectFallback` counted, `detail.workItemId`/`detail.threadId` omitted, `evidence: []`, `waiting: "nobody"`. Benign; the fact still records.
22. **Benign race — `report_block` and `clear_block` in one parallel tool batch**: if the clear's handler runs first, its `flush` returns before the report is enqueued and it answers `no-open-block`; the report then lands normally and the agent clears it on its next turn. No wrong fact is stored; nothing is lost.
23. **Benign race — two concurrent `clear_block`s on one open family**: both reads see the same open condition and two `block-cleared` documents with the same `clears` land; KPR-468 keeps the first clearing record (canon: "repeated clears preserve the first clearing record"), the second is inert at the ledger, and the epoch resolver still yields `generation + 1` on the next report. Two log rows, one clear.
24. **Read fault in `findOpenCondition`** (`clear_block` only — `report_block` performs no read; in tests also a throwing `enqueuePublish` double): the rejection reaches the handler's catch ⇒ `{ state: "unavailable", cause: "fault" }` with `isError` absent, `faults` counted, one warn line, nothing published by `hive-agent`. On either lane KPR-454 sees a successful call and records no `tool-failed` — the ops path's own read fault is logged and counted, never published (KPR-458 D10(a)). A rejecting **insert** never reaches this catch: it is Edge 13.
