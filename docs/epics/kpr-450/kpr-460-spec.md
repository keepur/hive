# KPR-460 — Model catalog scanner lifecycle and truthful freshness

## TL;DR

Run Claude, Codex, and Grok subscription discovery automatically every eight hours per instance, with an immediate startup check for unseeded or overdue catalogs. Reuse KPR-459's shared store and fenced attempt tokens so provider failures, restarts, overlapping ticks, and uncertain writes cannot erase a working catalog or claim a successful check that never committed. Expose the last catalog write, last successful discovery, latest attempt, and pending export separately through the existing catalog tool and an informational doctor section; KPR-461 owns CoS delivery.

## Key Points

- Use one engine-owned `ModelCatalogScanner` with a one-minute maintenance tick and independent provider lanes. Each provider starts at most one normal discovery every eight hours, anchored to its persisted attempt start; failures do not become one-minute vendor retries.
- Startup checks absent/empty catalogs and providers with no discovery history immediately, checks overdue providers, and respects active leases. A completed recent attempt on a seeded catalog is not repeated solely because the engine restarted.
- ⚠ An expired running attempt is unresolved interrupted work, not a recorded failure. Recover/reconcile first, then acquire a new UUID through KPR-459's lease rules if the current state still warrants it. The old outcome is never guessed.
- Keep the **same store instance** from fresh attempt acquisition through first `applyDiscovery`. KPR-459's bounded store-local proof controls submission; restarted stores and uncertain-token reentry reconcile only and wait for positive evidence or safe lease supersession.
- Successful unchanged discovery updates successful-check time without changing snapshot write time or creating history/change records. Manual refresh never changes discovery cadence or successful freshness; a later manual write is explicitly distinct from the most recent discovery check.
- Isolate discovery and storage failures by provider, retain the last committed models, and sanitize errors. Continue maintenance while agents are stopped; stop the scanner only on engine shutdown, abort external work, and drain for a bounded time before closing Mongo.
- ⚠ Start with fixed defaults: eight-hour discovery cadence, one-minute maintenance, two-minute attempt lease, and five-second shutdown drain. These are engineering constants with injected test clocks/timers, not new user configuration or hot-reload behavior.
- Gemini remains live-only and plugin catalogs remain manually maintained. Export recovery can cover all stored providers, but this child creates no notifications, dispatch callbacks, agent assignments, capability updates, or new catalog read tool.

## Problem, goals, and exclusions

The current engine never starts deterministic subscription-model discovery. Stored catalogs can age silently, and a catalog's `updatedAt` describes a saved list rather than the last successful vendor check. A heartbeat needs to survive partial provider failures and restarts without delaying engine startup, duplicating a provider's work, or treating an uncertain Mongo acknowledgment as a failed discovery.

This child owns timing, engine startup/shutdown, bounded local concurrency, interpretation of the shared store's outcomes, background export recovery, and readable freshness/status diagnostics. It must leave enough durable information to distinguish a recent successful check from a recent failed attempt even when the engine is offline.

Excluded: KPR-459's provider protocol/auth/normalization or writer redesign; KPR-461's CoS selection, delivery/retry/acknowledgment and notification diagnostics; Gemini polling/storage; plugin discovery; user model assignments; generation probes; scheduled agent turns; provider circuit-breaker changes; `LLM_CATALOG`; effort suffixes; Beekeeper; global default-agent routing; cross-instance coordination; deployment; KPR-320 and KPR-315. No cron entry, new Mongo client in the engine, extra scanner-status collection, or general scheduling framework is required.

## Lifecycle contract

Expose a small testable class with `start(): void`, `tick(): Promise<void>`, and `stop(): Promise<void>`. The constructor receives the shared store and discovery function; clock, UUID, timer, and timing overrides are injected for tests. Production imports one configured discovery function created by KPR-459. There is no dependency on `AgentManager`, the registry's assigned models, scheduler jobs, or `Dispatcher`.

`start` is idempotent. It starts an unreferenced one-minute interval and launches one immediate startup tick without awaiting provider network work. All started promises have rejection handlers. The engine must become available even if all provider credentials are absent or discovery is slow. Construction/start cannot perform a mandatory successful discovery or index write as a boot gate.

`tick` launches independently eligible provider lanes and the export-recovery task, returning when the work it launched settles. A lane is marked busy synchronously before its first await. A concurrent timer/test tick skips that lane, with no queued catch-up tick or replacement of its in-flight promise. A slow Claude lane cannot stop Codex/Grok from being considered by later ticks. The recovery task has its own no-overlap latch and cannot gate launching a provider lane. Use per-task containment/settled results rather than one unhandled rejection aborting a tick.

`start` called again while active is a no-op. `stop` is terminal for that object; subsequent `tick`/`start` calls do not restart work. A new engine lifecycle creates a new scanner. `agentManager.stopAll()`, registry reload, and ordinary agent disable/enable operations do not stop or recreate it. Each instance scans its own database independently, as approved; persisted leases also protect accidental duplicate scanner objects using that same database.

### Timing and eligibility

Use `SCAN_INTERVAL_MS = 8 * 60 * 60 * 1000`, `MAINTENANCE_INTERVAL_MS = 60_000`, and `ATTEMPT_LEASE_MS = 120_000`. KPR-459 already bounds discovery to 60 seconds; the lease leaves another minute for completion. It is a fencing deadline, not a guarantee Mongo finishes within a minute. No heartbeat extends a discovery lease.

At each provider lane's decision, read the latest persisted catalog state. Do not cache the last-attempt time as the authoritative schedule and do not use catalog `updatedAt`, manual version timestamps, or `lastSucceededAt` to postpone discovery. For a completed attempt on a seeded catalog, `nextAttemptAt = scan.startedAt + eight hours`, regardless of success or failure. Check `now >= nextAttemptAt`, so an exact-boundary tick is due. A delayed or suspended engine does one due attempt, never one attempt for every missed interval; the new persisted start anchors the next interval. The maintenance interval introduces at most approximately one minute of normal scheduling delay, excluding event-loop/storage delay.

Apply these rules in order:

| Observed state | Action |
| --- | --- |
| A local operation for this provider is still outstanding | Skip the provider. A timeout or expired persisted lease alone does not release this local no-overlap guard while an underlying store call is still running. |
| An unresolved local acquisition/completion identity is being tracked and its lease has not expired | Read/reconcile that identity only; do not start new external discovery or allocate a replacement attempt. |
| Persisted running attempt with an active lease, including one from another process | Skip discovery and leave its status untouched. Never resume another store's submission. |
| Persisted running attempt whose lease expired | Run the bounded reconciliation/recovery behavior below; if a fresh read still shows expired running work, acquire a new UUID through the store. This interrupted-work recovery is immediate rather than an eight-hour wait. |
| No scan history, including a nonempty legacy/manual catalog | Due immediately: no automatic check has established a schedule yet. |
| Absent/empty models at the first eligible startup check | Due immediately, even if a previous process recently recorded a failed attempt. Consume this startup opportunity once per provider; a failure in this process follows the normal eight-hour cadence. An active lease defers the opportunity until it can be considered safely. |
| Seeded catalog and completed scan with a valid start time | Due at the persisted start plus eight hours. Restart alone, stale successful freshness after a recent failed attempt, or a manual edit does not bypass this gate. |

If an attempt cannot be acquired or its state cannot be read, do not contact that provider. Retain a sanitized storage diagnostic and reconsider on a subsequent maintenance tick. `busy` does not count as a new attempt or failure. Provider discovery is limited to the exact KPR-459 built-in union, in its stable existing order; do not enumerate plugin providers or Gemini into the discovery loop. Missing credentials are handled as honest discovery failures, not a synthetic successful skip, and no paid API credential probe is added.

Invalid/missing scan dates and timestamps in the future must not produce a “recent” success or an unbounded scheduling delay. Expose unavailable/clock-inconsistent timing and consider a fresh attempt due once the persisted lease permits it. Never force-clear or bypass a future/invalid lease; the store's server-side lease checks remain authoritative, and an invalid lease that cannot be acquired is visible storage/state trouble. Normal production timestamps are BSON `Date` values; do not invent a successful timestamp from a legacy catalog's `updatedAt`.

### Attempt execution and the store-local proof

For a new attempt allocate one UUID, capture its start and two-minute lease expiry, and call `beginDiscoveryAttempt` on the long-lived scanner store. Keep this exact store object and attempt identity for the first `applyDiscovery`. The store, not the scanner, determines whether the acquisition established a never-submitted proof. `started` can also result from a reread after ambiguous acquisition; it does not give the caller permission to bypass the proof or reconstruct it elsewhere.

After a returned `started`, if the scanner is still active and the lease is not already expired, call the injected discovery function with that provider's abort signal. After discovery resolves, check cancellation/stopped state and lease again before calling `applyDiscovery`. The store rechecks its persisted token/revision/server-time filters; a local check is only an early exit. A raced/ambiguous `started` may yield rows followed by a reconciliation-only `applyDiscovery`; accept the resulting uncertainty and do not re-fetch to force progress. A thrown acquisition does not authorize external discovery, even if a later read finds the token.

No rows, hashes, or fresh-submission proof are persisted by the scanner. At most three provider lane records hold an attempt identity, controller, outstanding promise, and any rows needed for that active operation. Discard response rows after the initial apply returns; later reconciliation uses the same UUID and a non-replayed input with the existing store API. KPR-459's no-proof `applyDiscovery` branch reconciles before row validation, so a restarted store can call it with no replacement payload (for example `[]`) solely to look for positive evidence. This is not a new public replay API and must never enter the submission path. Do not call it as a reconciliation shortcut on a never-submitted local attempt whose proof is still ready.

Interpret outcomes as follows:

| Result | Required lifecycle behavior |
| --- | --- |
| Discovery throws a typed provider/auth/timeout/validation error before apply | Record that safe failure through `failDiscoveryAttempt` while active and while the token can still be completed. Preserve models and `lastSucceededAt`; the completed attempt schedules the next normal check eight hours from its start. |
| `committed`, with or without `recoveryPending` | The discovery succeeded. Read authoritative stored status as needed; do not call failure recording or undo the catalog. Pending projection is separate maintenance work. |
| `unchanged` | Successful check, no catalog content write/history/change. The shared store alone advances `lastSucceededAt`; cadence still uses the attempt start. |
| `not-committed` | This is definitive refusal supplied by the proof-aware store. Record a safe failure, including `storage` where applicable, if the token remains valid. Do not create an automatic immediate apply/re-discovery retry loop even if `retriable` is true; the normal next attempt is eight hours from this one's start. |
| `superseded` | Drop local response state and reread on a later tick. Do not record failure for the old token or mutate its successor. |
| `commit-unknown` | Retain the operation/attempt identity and uncertainty. Do not call `failDiscoveryAttempt`, replay rows, advance successful freshness, or allocate a new attempt until positive evidence or safe lease supersession permits progress. |
| Acquisition/failure-recording/storage call throws, or a started store call has not settled by its lease deadline | An error/deadline is not evidence that its mutation never happened. Retain the attempt identity, report storage/unfinished status, and follow reconciliation; do not turn a raw thrown error into a provider failure or free a still-outstanding local lane. |

Use KPR-459's `CatalogError`/safe-error helpers and fixed diagnostic text. No raw SDK/HTTP/Mongo/command exception, credential, URL bearer, or account metadata reaches logs or tool/doctor output. Logger name is `model-catalog-scanner`. Log attempt outcomes with provider, attempt ID, safe code/status, and recovery state; avoid a repeated warning every minute for the same unchanged error. A successful new check clears the prior provider error through the store's existing success update.

### Reconciliation and interrupted work

Read persisted state and recover pending exports on maintenance; after `applyDiscovery` returned `commit-unknown`, the proof-consumed same store or a fresh store can call `applyDiscovery` with that exact UUID for reconciliation only. An uncertain begin or failure-recording call that never entered apply instead uses read/recovery: its original store may still hold a ready proof, so do not pass placeholder rows to that store. Positive version/envelope evidence can establish the original changed commit. Positive `scan.outcome: succeeded` evidence establishes that a successful check was durably recorded even when the store's conservative unchanged-operation reconciliation lacks the captured old snapshot identity; do not label a later manual snapshot as that old check's content. The current document remains the authoritative view for freshness and future cadence.

An immediate negative read, unreachable history, failed index initialization, guard refusal now, or failed export recovery cannot establish noncommit of an earlier operation. Preserve uncertainty through all those paths. A restarted scanner does not call `begin` with an old UUID hoping to regain proof, reconstruct a fake successful result, or mark expired work failed. While an old lease remains active it waits. When the old lease has safely expired and the current document still has expired running work, a fresh UUID acquisition may supersede it under KPR-459's rules; once acquired, old completions remain fenced by token and server time. A late positive success observed before takeover returns to the normal schedule instead of triggering an unnecessary fresh request.

If an acquisition threw before its token was observable, retain that UUID and its supplied lease locally until it settles or expires. No new begin/provider request starts before then. After restart only durable evidence remains; the store's atomic claim/lease predicates must decide whether a new UUID can proceed. Never regard a local timer as proof that a Mongo mutation was canceled.

This design deliberately permits safe stalled work: if an underlying store promise never settles, that provider remains locally occupied and other providers continue. Show unfinished/expired state; shutdown/restart can recover through persisted leases. Do not release the latch and create arbitrarily many uncancelable operations merely to make a timer appear healthy.

## Export maintenance and sibling boundary

Launch `recoverPendingExports()` once at startup and on the one-minute maintenance tick, guarded against an overlapping recovery sweep. This recovers pending exports for built-in and manually maintained plugin catalogs without discovering plugin/Gemini models. It can run independently of a provider's eight-hour schedule, successful discovery, or notification availability. KPR-459 catches export failures per provider; contain a sweep-level exception as storage trouble and retry on a later tick. Provider writes keep their own required recovery step, so a slow all-provider sweep never becomes a global prerequisite for discovery or correctness. Competing export recovery is idempotent under KPR-459.

Report `pendingExport` as recovery pending until it is actually cleared. A successful catalog commit remains readable and successful while its audit/change export is pending; a later replacement may be refused until projection succeeds. A failed recovery must not refresh discovery success or become a vendor error.

KPR-461 consumes the durable change collection and may add its own delivery wakeup/timer after routing is ready. It need not receive an in-memory scanner callback to avoid losing changes. This child never calls `Dispatcher`, selects a recipient, changes a delivery subdocument, or interprets catalog freshness as notification acknowledgment. KPR-461 should reuse this maintenance ownership where appropriate, rather than require a successful scan before considering pending/recovered notices.

## Shutdown contract

At the beginning of engine shutdown, call `stop` before closing Mongo or waiting through unrelated subsystem shutdown. It synchronously sets the stopped latch, clears the interval, aborts active discovery controllers, and prevents subsequent scanner steps from starting new begin/discovery/apply/failure/recovery calls. Check that latch after awaited acquisition and discovery and before each new scanner-level store call.

Wait for the scanner's already-started tasks for at most `SHUTDOWN_DRAIN_MS = 5_000`, using an observed settlement race. Multiple `stop` calls share the same drain result. A late provider response is discarded. KPR-459's Claude cleanup and HTTP cancellation run; a started Grok credential rotation may finish its safe writeback as specified there, but cannot lead to a model fetch/apply after cancellation.

A store call already started before `stop` is not cancelable through the planned store API. It may finish its internal journaled commit/export sequence during or after the drain; preserve its outcome and observe rejection without starting another scanner operation. Do not stamp a canceled/failed status over an uncertain apply, or claim that `stop` rolled back an accepted commit. If the drain expires, leave the persisted attempt/envelope for restart recovery, log a fixed incomplete-drain diagnostic, and permit normal Mongo/process shutdown. No pending export is deleted. This bound concerns scanner shutdown only and does not promise the engine's other shutdown operations finish in five seconds.

## Truthful catalog and doctor diagnostics

Derive a provider status from the persisted document and an injected current time. Keep three independent facts visible:

1. **Saved catalog:** seeded/unseeded, model count, latest history-bearing write time, and provenance `manual`, `discovery`, or `legacy/unknown` when absent. Existing entries keep `source: "curated"` and `asOf = updatedAt`; that compatibility field is explicitly the saved-list timestamp.
2. **Successful discovery:** `scan.lastSucceededAt`, its nonnegative age when valid, and “recent” when age is less than eight hours, “overdue” at eight hours or older, or “never” when absent. An invalid/future date is “unknown/clock-inconsistent,” never recent. These labels describe the last discovery check, not proof that a later manual snapshot was validated.
3. **Latest attempt and storage:** attempt start/outcome, safe error and finish time when failed, running lease expiry or expired/unresolved state, next normal attempt time where known, plus recovery pending. A failed latest attempt remains visible even if the last successful check is still recent. A running/expired attempt does not fabricate an error, successful finish, or new freshness.

Use prose provider notes in `agent_model_catalog_list` for these facts, after the unchanged entries JSON. Include a status note for each requested built-in, including success, so unchanged checks have an observable fresh timestamp. For an unseeded built-in retain the existing unseeded meaning and manual-refresh option while explaining automatic discovery status. Plugin notes describe manual maintenance and any pending export without invented discovery expectations; Gemini remains on its existing live/cache/error path. A stored catalog remains listable when its latest discovery failed, with the failure and old successful-check time plainly attached. List calls do not trigger built-in discovery or export recovery.

Keep per-provider catalog reads contained so a provider-specific storage failure can produce an unavailable note alongside other successful results. Never convert an unreadable document to “not yet seeded.” A request for one stored provider whose state cannot be read returns a safe error; multi-provider reads return available entries plus unavailable notes. Preserve the existing Gemini-only hard-error behavior and all-provider partial behavior. Unknown-provider validation and legacy JSON entry ordering remain compatible.

The doctor's read-only adapter queries the catalog collection directly using the CLI's existing short-lived-client pattern and closes its client. It returns an explicit unavailable result for a failed database read, distinct from a successful read with missing catalogs. It must not instantiate discovery, recover exports, initialize catalog indexes, or import runtime configuration/SDK code through the status module. Render all three built-ins in the stable order and any stored plugin rows as manual; never query Gemini or imply a persisted Gemini baseline. Doctor freshness derives from catalog scan fields, not a newly written telemetry timestamp. The section is informational and does not change `allPassed` or the exit code.

Illustrative note: `codex: saved 2026-09-07T14:00:00Z (manual); last discovery success 2026-09-07T12:00:00Z (overdue); latest attempt failed at 20:00:12Z (auth); next attempt 2026-09-08T04:00:00Z.` A recent manual edit in this example is not shown as a successful vendor check. Recovery warnings are added independently when present; display strings are not a new machine-consumed API.

| Required flow | Observable assertions |
| --- | --- |
| First boot / legacy / empty catalog | One immediate attempt per eligible built-in; legacy manual `updatedAt` is not discovery history; active leases defer safely; status-only document remains unseeded; Gemini/plugins never discovered. |
| Cadence and restart | Seeded recent success/failure skips startup; exact eight-hour boundary is due; failures do not retry every minute; missed intervals do not burst; manual refresh changes neither due time nor successful freshness; unseeded startup override is consumed once per provider. |
| No overlap and isolation | Overlapping `tick`/`start` calls yield one provider lane; one delayed/rejecting provider, stuck store call, or recovery sweep leaves other lanes able to finish and start when due; no promise rejection leaks. |
| Success / failure / unchanged | Compare persisted models, audit/change counts, catalog `updatedAt`, `scan.startedAt`, `lastSucceededAt`, and errors. Unchanged success changes only successful scan state. Provider/auth/empty/malformed/timeout failure preserves saved content and prior successful freshness. |
| Same-store fresh submission | Acquire through the scanner's long-lived store and prove a normal discovery commits. Acquiring through one store then accidentally constructing another for initial apply must fail the test's expected successful flow; no plan may paper over it by bypassing proof. |
| Ambiguous begin and completion | Delayed begin does not start external discovery until `started`; thrown begin retains its UUID until safe expiration. Changed and unchanged ambiguous writes, unavailable evidence, guard engagement, and recovery failure never call failure recording or replay submission. Positive evidence updates the displayed truth without inventing a captured snapshot identity. |
| Restart / expired-token takeover | Fresh store performs reconciliation-only old-token calls. Active old lease prevents a new request. Expired running state allows a fresh UUID only through the real store predicates; a delayed old success/failure has no effect after takeover. A success seen before takeover returns to cadence. |
| Export maintenance | Startup and a later minute tick recover committed pending exports even when no provider is due, including a manual plugin change; duplicate recovery does not mutate delivery fields; a failed provider export does not cancel successful provider discovery. |

| Diagnostics | Tool and doctor agree for legacy/unseeded/recent/overdue/failed/running/expired/recovery-pending states, future/invalid dates, and read failure. ## Assumptions and review notes

- Non-blocking delegated choice: cadence is anchored to the persisted attempt start, not success. A recent failed attempt therefore leaves visibly overdue successful freshness while waiting for its next eight-hour attempt. Unseeded startup and expired interrupted work are the explicit immediate-recovery exceptions.
- Non-blocking delegated choice: the scanner is always enabled for the three built-ins, with fixed production intervals. Discovery controls its own existing credential availability; adding disable/provider/cadence configuration is unnecessary for this ticket.
- Non-blocking delegated choice: one minute is a maintenance/recovery poll, two minutes is a nonrenewed attempt lease, and five seconds bounds scanner drain. A persistently stuck store call can stall that provider until restart; preserving no-overlap and uncertainty is preferable to spawning unbounded operations.
- Non-blocking compatibility constraint: entry `asOf` retains its saved-catalog meaning; successful-check freshness appears in explicit status notes. A successful prior check is never an assertion that an intervening manual replacement was checked against the vendor.
- Non-blocking dependency limitation: KPR-459's proof and unchanged reconciliation are conservative. A freshly constructed store can observe successful scan state without being able to reconstruct an old unchanged operation's snapshot identity; this child uses that state for scheduling/freshness and never manufactures a replacement result.
- No blocking product question remains. These choices fit the approved Gate 1 scope and must be independently reviewed before planning.
