# KPR-461 — CoS catalog-change notifications and integration verification

## TL;DR

Consume KPR-459's durable catalog changes independently of discovery and notify a validated CoS through a targeted system WorkItem and its resolved Slack home base. Retain the change until both successful CoS processing and an explicit Slack acceptance receipt are recorded; normal transport retries reuse durable prepared output, while an ambiguous crash can repeat a notice rather than lose it. Verify the complete scanner/manual-write → recovery → recipient → dispatch → acknowledgment flow without live provider calls, operator Slack messages, or assignment changes.

## Key Points

- Bootstrap and added/removed model IDs produce one notice per committed change, including manual/plugin changes. Names, notes, ordering, unchanged discovery, and failed discovery produce no new notice; a later unchanged scan cannot cancel pending work.
- Select the sole enabled `isDefault` registry agent. With zero defaults, accept an explicitly configured `DEFAULT_AGENT` only if it resolves to an enabled agent; multiple defaults fail closed. Preserve configuration provenance so the implicit `chief-of-staff` fallback cannot become a notification recipient.
- ⚠ Use the selected agent's configured Slack `homeBase`, resolved through the connected Slack gateway. Missing home base, unsupported bot binding, unresolved destination, or invalid recipient keeps the change pending with a visible reason; no guessed channel, generic audit fallback, or global routing repair.
- Add a narrow outcome-aware system-notification path inside `Dispatcher`. Existing `dispatch(): Promise<void>`, `ChannelAdapter.deliver(): Promise<void>`, and the gateway's best-effort posting helper are not acknowledgment evidence.
- ⚠ Persist successful CoS processing and the exact bounded outgoing message before posting it. A transport retry reuses that preparation; success requires a validated Slack `ok`, channel ID, and message timestamp. This proves processing completion and transport acceptance, not human readership or any subsequent assignment decision.
- Use journaled outbox claims, renewable leases, fenced state transitions, capped retry backoff, and stable `commitId` work identity. Never silently expire, delete, coalesce, or exhaust a pending notice; uncertain database/network outcomes remain uncertain until evidence or a safely fenced retry.
- ⚠ One engine-owned notifier polls every minute after Slack wiring, with one active local delivery and bounded batches. It operates independently of the eight-hour scanner and shares the guarded database; shutdown stops both subsystems before other teardown.
- Application integration tests cover the real catalog store/scanner/notifier/dispatcher/Slack receipt path, plus a real `AgentManager` turn-entry slice with an injected provider runner. Gemini stays live-only; assignments, provider capabilities, effort suffixes, Beekeeper, and broad routing/default repair remain outside scope.

## Problem, goals, and exclusions

A committed catalog change can currently be followed by no CoS message at all: there is no scanner notifier, recipient defaults are unreliable, and existing dispatch/delivery methods can resolve after skipping work or swallowing a failure. An in-memory callback or a scheduler event marked fired before recipient validation would lose recovery evidence. Retrying an entire successfully processed agent turn after every Slack failure would also create duplicate CoS work.

This child owns outbox delivery state, validation of the CoS and destination, the explicit preparation/delivery seam in the dispatcher, engine lifecycle, notification diagnostics, and application integration verification. Catalog writes never await a CoS, transport, or approval. Once a change has been exported, notification trouble cannot block later catalog replacements.

Excluded: provider discovery/auth changes, rewriting sibling CAS/freshness semantics, a general durable messaging framework, event-bus migration, generic dispatcher return-type conversion, a new scheduler job, new credentials or Slack bot, new public admin tool, retention/dead-letter deletion, global default/Slack routing changes, automatic assignment or effort/capability updates, Gemini polling/storage/diff baselines, Beekeeper, deployment, KPR-315, and KPR-320. Agent turn machinery retains its existing admission, budgets, sessions, and telemetry; the notifier supplies no model override and writes no agent definitions or per-agent configuration.

## Grounding in current code

- `src/agents/agent-registry.ts`: `getAll()` exposes active loaded agents; disabled definitions are kept separately. `getDefault()` returns the first match and cannot detect multiple defaults. Use the full current enabled snapshot for this feature, and validate again before starting each external stage.
- `src/config.ts`: `optional("DEFAULT_AGENT", "chief-of-staff")` resolves environment/loaded `.env`, then the existing Keychain helper, then the literal fallback. Capture the explicit value using that same existing resolution once, without the literal fallback; expose an optional companion field for this consumer. Keep the existing `config.defaultAgent` value and all its other consumers unchanged. Never inspect or print stored credentials to infer provenance.
- `src/channels/dispatcher.ts`: ordinary dispatch adds its one-minute message dedup entry before routing, can return for no agent/disabled agents, falls through after an invalid explicit target, suppresses nonresponses, and catches turn failures. Its delivery helper catches transport errors and puts results into a separate retry queue. Neither its return nor that queue establishes this outbox's completion.
- `src/agents/agent-manager.ts`: `runWorkItemTurn(agentId, item)` performs session lookup and calls `spawnTurn`; `TurnResult` has final text, errors, and separate timeout/abort flags. A resolved turn is not necessarily successful. The method exposes no per-call cancellation handle, and spawn admission/queueing can outlive a nominal provider timeout.
- `src/channels/slack-adapter.ts` discards the result of `gateway.postMessage`. `src/slack/slack-gateway.ts` catches posting errors, can fall back to another post after an identity error, and returns `undefined` on failure; long messages split or upload files. A new receipt-bearing single-message path is necessary for this feature. Preserve ordinary adapter/gateway behavior.
- `src/index.ts` constructs the guarded database and dispatcher before starting channel adapters, and KPR-460 plans scanner startup before Slack startup. Start the notifier after the Slack adapter is connected and its receipt path is available. It can consume changes committed before that point without an in-memory scanner callback.
- `src/admin/model-catalog-status.ts` and the catalog/doctor changes in KPR-460 provide the planned existing diagnostic surfaces. Append notification status without redefining saved-list time, successful discovery, or provider failure.

## Change identity and message contract

Consume only immutable `agent_model_catalog_changes` rows produced or recovered by KPR-459. Their `_id` is the catalog `commitId`; payload fields are provider, revision, snapshot identity, creation time, source, actor, bootstrap, added IDs, removed IDs, and model count. Do not recompute the diff from the latest catalog, reinterpret `commit-unknown` as a notification event, or create retrospective events for legacy catalogs. A recovered committed envelope is as eligible as a freshly exported row. An ambiguous catalog commit yields a notice only when its exact durable change actually becomes available.

Use `WorkItem.id = "catalog-change:" + commitId`, stable across ordinary retries and restarts. A stable thread ID derived from the same change and selected agent keeps retries of that change in the same agent session while separating distinct changes. Use `sender: "system"`, a typed catalog-notification discriminator created only by the engine's dedicated entry point, and the exact `meta.targetAgentId`. Set the source to the resolved Slack destination and adapter, with no conference, outage-replay, deadline-retry, mention fan-out, or synthetic Slack timestamp metadata. A generic inbound message merely containing that metadata must not gain access to the special entry point.

The prompt must identify the committed provider/revision/time, `discovery` versus `manual`, bootstrap versus ordinary membership change, model count, added/removed counts and IDs, and stable change ID. Say that the list is already saved, ask the CoS to raise any proposed assignment decision with the operator, and explicitly state that this notice does not authorize changing an agent's model. It is historical change evidence, not a claim that the revision is still the latest catalog. Model IDs, provider names, and actor strings are data: encode/escape them inside the fixed template rather than treating them as instructions or Slack mentions. Do not copy manual notes or arbitrary change-summary prose into the notification prompt.

Bound the prompt to 12,000 characters and the final Slack message to 3,900 characters including headings and any signature. Include full ID lists when they fit; otherwise show a deterministic bounded prefix from each list, exact totals, and explicit omitted counts. Never truncate away provider, revision, bootstrap/source, or change identity. The immutable outbox/history retains the complete change. If an individual identifier exceeds the display budget, label its displayed value as shortened. A bounded summary is not a loss of the durable event.

The outgoing message always includes the deterministic change summary and the request to bring assignment decisions to the operator. It may include a bounded excerpt of the CoS's final response when present; identify an excerpt as shortened. An otherwise successful empty/recognized nonresponse still prepares and posts the deterministic summary, so suppression cannot discard the notification or repeatedly run a successfully completed turn. A failed, aborted, or timed-out turn cannot use this fallback to claim successful CoS processing.

Illustrative content: `Codex catalog updated — revision 8, discovery, 2026-09-07T20:00Z. Added: model-a. Removed: model-b. 9 models total. Change <commitId>. Please raise any assignment proposal with the operator; catalog maintenance has not changed agent assignments.` Bootstrap instead explicitly says `Initial catalog seed` and summarizes all additions, with omitted counts if needed.

## Recipient and destination selection

Resolve from one current enabled registry snapshot, not from names in message text or an agent's assigned model:

| Registry/config state | Result |
| --- | --- |
| Exactly one enabled agent has `isDefault === true` | Select that agent, regardless of the explicit fallback value. |
| More than one enabled default | Pending `multiple-defaults`; do not select the first or consult the fallback. |
| Zero enabled defaults; explicit `DEFAULT_AGENT` resolves to an enabled registry agent | Select that exact ID. An explicitly configured literal `chief-of-staff` is valid only under the same existence/enabled check. |
| Zero defaults and missing, blank, unknown, or disabled explicit fallback | Pending `recipient-missing`; implicit defaults and disabled definitions are not candidates. |

The destination is the selected agent's nonblank `homeBase`, resolved by the connected Slack gateway to a channel ID. Do not invent `agent-<id>`, take the first `channels` entry, broadcast, use an arbitrary DM, or use the global audit fallback. For an agent with an explicit `slackBot` binding, require an available matching adapter; today's single primary-adapter engine must return `transport-unavailable` if it cannot honor that binding. Adding multi-bot initialization is out of scope. Channel-name caches are routing hints; a resolved ID alone is not proof Slack accepts the post.

Re-resolve eligibility before the CoS turn and before the Slack send, after any awaited destination lookup or preparation write. Freeze the selected agent, configured home-base identity, resolved channel, and adapter for each external operation. If the current selection/destination differs before that operation starts, do not send using stale routing; return pending and reevaluate on a later attempt. No fallback through generic `resolveAgents` is allowed if the explicit target vanished.

Durable prepared output is reusable only for the same selected agent, configured home base, and resolved transport destination. If that binding changes between attempts, prepare the immutable change for the newly validated CoS and replace the old preparation under the current claim before sending. Preserve the event and an explicit recipient-change/previous-uncertainty diagnostic, rather than permanently stranding the old binding or presenting another agent's response as the new CoS's. A previously acknowledged/delivered row is terminal and is not resent solely because the default later changes. A selection change cannot undo an already-started turn or post; if that post receives a valid acknowledgment, record the actual recipient/destination that accepted it. An uncertain earlier send followed by recipient reassignment can notify both recipients; this is reported as possible duplication, not represented as exactly-once delivery.

## Explicit dispatch and transport outcomes

Add a focused typed system-notification seam to `Dispatcher`, with two stages that the notifier can durably separate. Exact method names are a planning choice, but the following outcomes are binding:

1. **Prepare:** validate the exact target/destination and execute the targeted WorkItem through `AgentManager.runWorkItemTurn`. Return either `prepared` with successful processing evidence and the exact bounded outgoing message, or a typed retryable/unresolved result with a fixed safe reason. Successful processing requires `errors.length === 0`, `aborted !== true`, and `timedOut !== true`. A thrown admission/provider error is not preparation. Preserve the normal manager's session and resource machinery; do not call an SDK directly from the notifier.
2. **Send prepared:** accept only the current claim's persisted preparation, revalidated route, and fixed outgoing text. Perform the explicit receipt-bearing Slack delivery and return `acknowledged` with `{ channelId, messageTs }`, `not-accepted` for a documented definite refusal/no-submission, or `outcome-unknown` when acceptance cannot be established. Receipt validation must require `ok === true`, a nonblank Slack timestamp, and the expected channel ID. A resolved promise with no receipt, mismatched channel, malformed response, or network/timeout ambiguity is not acknowledgment.

The notifier writes the preparation durably before calling stage two. A definitely failed/unconfirmed Slack attempt keeps it, so a later retry does not repeat a successfully prepared CoS turn. Preparation is not `delivered`; an in-memory dispatch acceptance, a queued spawn, successful health/audit post, existing one-minute dedup hit, or scheduling of another retry is also not `delivered`.

Implement the narrow path inside the existing dispatcher/adapter/gateway boundary, preserving normal `dispatch` behavior and types. It must not invoke generic `recentMessageIds` dedup, status-query interception, fuzzy routing, conference fan-out, audit mirroring, global retry queue, outage queue, or deadline continuation for this special notice. Those paths cannot report their later outcomes back to this outbox and would create competing retry owners. AgentManager still enforces its provider circuit breaker and ordinary resource rules; a refusal simply leaves this notification pending. If shared helpers are extracted, their default semantics and all ordinary callers remain unchanged.

The Slack gateway's additive receipt method posts one bounded message using the existing authenticated connection, with no identity-fallback second post, split, file upload, or untracked retry handoff. Use a plain bot post with agent identity included in the fixed text; no new impersonation capability or scopes are required. Disable automatic request replay for this additive operation where the installed client permits it; if a focused receipt client is needed to set operation-specific retry/timeout options, keep it inside the gateway, reuse its existing token/configuration, and do not change ordinary clients' policies. The plan must verify the installed Slack client's actual retry controls. Apply a 30-second request bound, respect an explicit rate-limit delay as a lower bound on retry time, and classify all uncertain failures conservatively. An HTTP/API response saying a message was refused can be `not-accepted`; a timeout or disconnected response cannot establish nonacceptance. Maintain the gateway's outbound timestamp cache on acknowledged posts so the system's own notification cannot trigger another inbound agent turn.

[Slack's method documentation](https://docs.slack.dev/reference/methods/chat.postMessage/) describes successful message responses, the destination field, and a recommended 4,000-character text size. The 3,900-character single-message bound is a local engineering choice. A Slack acknowledgment proves server acceptance only; there is no human-read receipt or guarantee that the CoS will later raise a proposal. This specification adds no exactly-once claim based on a message UUID.

## Durable outbox state and fencing

Extend only the mutable `delivery` subdocument supplied by KPR-459. Preserve every immutable payload byte/value and that child's exact duplicate-export comparison, which deliberately ignores delivery. Use the same guarded `Db`, existing typed changes collection, standalone-compatible acknowledged journaled writes (`w: 1, j: true`), and no sessions, transactions, change streams, second production Mongo pool, or TTL. Pending query semantics must include both due pending rows and recoverable expired claims, rather than relying on the sibling's initial pending-only helper.

Required logical fields are:

- `state: "pending" | "claimed" | "delivered"`, existing `attempts`/`nextAttemptAt`, and a monotonically advancing delivery `version` (absent on initial sibling rows means zero).
- Current claim token, owner generation, claim start/lease expiry, last attempt time, and stage (`preparing` or `sending`) while claimed. Claims use fresh UUIDs, distinct from the stable catalog/work ID. Keep `attempts` as acquisition attempts, not alleged CoS receipt counts.
- Optional durable preparation: selected recipient and route binding, successful processing time, exact outgoing text, and a preparation identity/digest. Bound it; do not store raw SDK objects, conversation transcripts, credentials, or exception text. Keep preparation across releases/reclaims while its binding remains valid.
- Latest fixed safe diagnostic/time and an uncertainty indicator, independent of catalog/provider status. Retain a previous uncertain-send indicator when retrying so diagnostics do not claim an unambiguous first send.
- Terminal receipt: actual recipient, adapter/channel, message timestamp, acknowledged time, and the matching preparation identity. A terminal row retains its event identity for deduplication.

No unbounded embedded attempt history is required. A pending row is never removed at an attempt limit. Malformed/unknown delivery states are visible storage/state trouble, never treated as delivered or deleted; known initial sibling rows work without an eager migration.

### Acquisition and active ownership

Read a bounded page of due candidates, ordered by `createdAt` and `_id`. Atomically claim one candidate by exact `_id`, observed delivery version (including absence), eligible state/due time or expired lease, and a proposed future lease. All mutations advance the version; this prevents a delayed claim using an old eligibility read from replacing a successor after it has completed or returned to pending. Pending eligibility uses `nextAttemptAt`; expired claimed eligibility requires a valid expired lease. Missing/malformed claimed leases fail closed and appear in diagnostics. No upsert can create a replacement event.

Check claim deadlines against Mongo's operation timestamp and resampled local time, following the sibling's documented `$$NOW` limitation. An operation admitted before expiry may install or acknowledge expired state after a server pause. Only a definitively acknowledged acquisition, still current and unexpired after response, permits this invocation to start external work. An acknowledged miss means no claim; reevaluate later. A thrown claim mutation is uncertain: do not start a CoS turn or send after an evidence reread merely finds a token. Keep its identity until bounded reconciliation or expiry; a fresh process waits out an active claim and acquires a new token from a fresh eligible observation. Negative/unavailable evidence does not prove the old write will never execute.

Use a two-minute claim lease, renewed every 30 seconds while an external stage is outstanding. Renewal is a conditional update for the exact current claim and active state, requiring the old lease to remain valid; it cannot resurrect an expired claim. Proposed dates never move backward, and stale renewal writes must compare the observed lease/version or be serialized so an older renewal cannot shorten/replace a newer one. An uncertain renewal or lost token prevents new external stages until current ownership is established by bounded evidence; an already-started operation remains observed. Keep one local delivery invocation busy until its underlying promises settle, even if a timeout or lease expires. A separate claimant may recover an expired claim; it must receive a new token, fencing every old preparation/release/renewal/acknowledgment write.

Before each CoS turn or Slack request, require a current invocation, active notifier, positive claim ownership and unexpired lease, and current validated route. After each await, recheck before starting the next external stage. Mongo leases cannot atomically fence a Slack HTTP request: a process can pause after its last check, or a request already in transit can complete after takeover. These are uncertain external outcomes that may duplicate; token fencing protects stored state and prevents knowingly stale work from beginning its next stage. Neither renewal nor local clocks justify an exactly-once guarantee.

### Preparation, acknowledgment, and uncertainty

Persist preparation with an exact-token/state conditional write; do not send until positive evidence identifies the intended durable preparation. A write exception with negative/unavailable reads remains uncertain and does not authorize another CoS turn or a send. While the original invocation remains alive, retain its prepared result for reconciliation and repeat only a demonstrably safe/idempotent state transition. A fresh claimant uses positive persisted preparation or runs the targeted notice again; loss between CoS completion and durable preparation can repeat CoS processing, an explicit crash/uncertainty limit.

Only a validated transport acknowledgment allows the conditional transition to `delivered`. The write must match the claim token and preparation identity so a late old acknowledgment cannot mark a successor's preparation delivered or clear its claim. If the lease expired but no successor has acquired the row, a known receipt may still finish that same token; do not discard real acceptance just because acknowledgment was delayed. If the token no longer matches, preserve the successor and surface the stale outcome diagnostically. The recipient and receipt refer to the actual posted preparation, not a newly resolved default.

If the delivered-state write throws, retain the receipt locally and reconcile the exact row before any further external action. Positive terminal evidence establishes completion. Negative/read-failure evidence remains unknown; it is not permission to resend immediately or reset delivery. While the receipt is available and the token still owns the row, retry only its idempotent acknowledgment transition, never the Slack post. After a crash, a post accepted before its durable acknowledgment may be repeated from the persisted preparation; no absence query can prove the earlier Slack post did not happen. Do not add a Slack-history search as an exactly-once oracle.

For a resolved failed attempt, conditionally release to pending with its safe reason, retained preparation when reusable, and next retry time. A release that is refused or whose acknowledgment is ambiguous cannot delete the event or release a newer claim. Preparation, terminal acknowledgment, release, and renewal operations must have distinguishable positive evidence; generic `modifiedCount === 0` or a negative read must never become a successful-delivery result. Outstanding uncertain database calls keep the local latch; do not race a timeout and immediately start a second mutating operation whose predecessor can still commit.

[MongoDB's atomicity guidance](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) supports conditional single-document transitions; it does not make those transitions atomic with a provider turn or Slack post. Reuse the siblings' adversarial fake and real standalone harness to prove these boundaries.

## Retry, lifecycle, and observability

Add an engine-owned `ModelCatalogNotifier` with idempotent `start`, callable `tick`, and terminal bounded `stop`. Poll immediately at startup and every minute using an unreferenced timer. Consider up to ten due changes per tick, process them sequentially, and hold a synchronous no-overlap latch for the whole local tick; no queued catch-up tick or unbounded in-memory backlog. Retry delays after resolved unsuccessful acquisitions are 1, 5, 15, then 60 minutes, capped at 60 minutes thereafter; a server-specified rate-limit delay can extend the next attempt. A read/claim miss is not a processing attempt and must not increment counters by guesswork. Future/invalid timing is shown as unavailable/clock-inconsistent rather than silently considered healthy; never bypass an active or malformed lease to force progress.

Later changes can be delivered while an older failed change waits for backoff. No strict cross-provider or delivery-time revision ordering is promised: messages carry committed revision/time, and each event stays independently recoverable. A slow CoS turn can delay this instance's other notifications; discovery, manual writes, and export recovery continue. The selected bounded serial consumer is sufficient for catalog-change volume and avoids another general queueing framework.

Start after Slack connection/adapter wiring and after the existing spawn-capable boundary. Construction/start must not require a successful CoS turn, Slack post, or index operation to complete engine boot. KPR-460 continues recovering exports every minute for all stored providers; the notifier independently queries the resulting outbox whether a scan succeeds, fails, is not due, or manual/plugin work caused the change. It does not call discovery or create change rows. Recipient recovery is picked up by the next eligible retry; no new registry watcher or per-agent timer is necessary.

At the beginning of shutdown, synchronously stop both scanner and notifier before awaiting either drain or any other subsystem teardown. This intentionally refines KPR-460's then-only `await modelCatalogScanner.stop()` first-statement wiring: invoke both stops first, then await their bounded drains together, and update that sibling's source-order assertion to the stronger two-subsystem invariant. Each retains its five-second drain; no new work starts while shutdown waits for the other subsystem. Clear polling/renewal timers, forbid new turns/posts, and observe all already-started promises. The notifier may record a receipt from an already-started send within its drain while Mongo is still available. After drain completion it starts no further store calls. It cannot promise to cancel `runWorkItemTurn` or roll back already-submitted Mongo/Slack work; leave claims/preparation for restart recovery. Engine `agentManager.stopAll()` and ordinary registry changes do not own either heartbeat's lifecycle.

Use `createLogger("model-catalog-notifier")` and fixed safe diagnostic codes, such as `recipient-missing`, `multiple-defaults`, `destination-unresolved`, `transport-unavailable`, `turn-failed`, `turn-interrupted`, `delivery-unconfirmed`, `recipient-changed`, `lease-lost`, `storage`, and `invalid-state`. Include provider/change ID, attempt count, stage, and retry time; never raw provider exceptions, HTTP bodies, authorization headers, account metadata, or generated reply text. Log transitions/backoff changes instead of a warning on every unchanged poll. A database-wide failure can only be logged while durable writes are unavailable; do not claim it was persisted.

Append read-only notification notes to the existing catalog tool and doctor's informational model-catalog section. Show per-provider pending count, claimed/in-progress count, oldest unresolved change age/ID, earliest scheduled retry or active lease expiry, latest safe blocking reason, and last acknowledged delivery time when present. Include plugin-provider changes as manual-origin notifications. Show pending export separately: no exported row yet is not proof that no notice is due. A failed outbox read is `notifications unavailable`, not zero pending. A delivered row must be described as `CoS processed; Slack accepted`, never `operator read` or `assignment approved`. Keep catalog JSON entries and all existing freshness semantics intact; doctor notification status does not change exit code or `allPassed`. Both readers remain strictly read-only, with no index initialization, claims, recovery, or dispatch. No separate telemetry collection is necessary.

## Assumptions, limitations, and review notes

- Non-blocking delegated choice: the CoS's configured Slack home base is the destination, without a guessed or generic fallback. Unavailable bindings remain visible and recoverable; adding multi-bot wiring or another destination policy is separate work.
- Non-blocking delegated choice: a notification completes after a successful CoS turn and Slack server acknowledgment. Persisted preparation avoids rerunning that turn for ordinary transport retries; deterministic summary text covers successful silence. This is stronger than dispatch acceptance and makes no claim about human readership or later action.
- Non-blocking delegated choice: a one-minute poll, ten-item serial batch, two-minute renewable claim, 30-second renewal/request bounds, capped one-hour retry backoff, and five-second shutdown drain are fixed engineering constants with injected test overrides, not new user configuration.
- Non-blocking limitation: external side effects cannot be atomically fenced with Mongo. Pauses, network ambiguity, crash before preparation/ack persistence, recipient changes after an uncertain send, or an already-started request finishing after lease loss can repeat processing or delivery. Stable identity, reusable preparation, receipts, and fenced state prevent ordinary retries from inventing completion or losing the event; exactly-once delivery is not promised.
- Non-blocking integration adjustment: KPR-460's first-statement scanner-only stop assertion must become a both-latches-before-await assertion in this child. Scanner timing/store semantics remain binding; this is required to prevent notifications starting during the scanner's shutdown drain.
- No blocking product question remains. These choices fit the approved Gate 1 package and require independent specification review before planning or implementation.
