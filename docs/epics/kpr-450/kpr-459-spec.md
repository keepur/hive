# KPR-459 — Subscription model discovery and shared persistence

## TL;DR

Provide deterministic Claude, Codex, and Grok subscription-model discovery and one shared replacement writer for discovery and the existing manual catalog tool. Every committed replacement is recoverably coupled to its history and, when model IDs change, a durable pending notification; this works on standalone MongoDB. KPR-460 owns when discovery runs and diagnostics presentation; KPR-461 owns notification delivery, with neither agent assignments nor Gemini storage changed here.

## Key Points

- Claude uses the installed SDK's control-only `supportedModels()`; Codex uses the ChatGPT subscription models endpoint; Grok uses the subscription CLI proxy models endpoint. Reuse subscription credentials, with no API-key or public-catalog fallback and no generation probes.
- Codex includes only `visibility: "list"`, orders by ascending vendor priority, and retains models with `supported_in_api: false`.
- Manual refresh remains a full replacement for built-ins and registered plugin providers. A later successful built-in discovery replaces membership, display names, and order while retaining notes and `addedAt` for retained IDs; plugins are never discovered automatically.
- Successful unchanged discovery advances discovery freshness only. Failure, malformed data, or an empty result preserves the catalog and successful-check timestamp; manual writes never advance discovery cadence or freshness.
- ⚠ A compare-and-swap commit and one bounded pending-export envelope in the catalog document replace the current unsafe two-write sequence. Recovery copies that envelope to history and the change outbox before accepting another replacement; no transactions, Mongo leases for manual writers, or unbounded embedded queues.
- Bootstrap and added/removed IDs produce one durable change per commit, including manual/plugin changes. Names, notes, and ordering do not produce notifications. Pending delivery never blocks catalog updates once the outbox record exists.
- ⚠ Persisted attempt tokens fence late discovery results; concurrent manual/scanner replacements compare against the latest committed snapshot. Shared status and change types below bind both siblings, while timers, recipient selection, and delivery acknowledgments remain their work.
- ⚠ Subscription APIs and SDK authentication metadata can change. Fail closed and expose a sanitized diagnostic; the successful provider checks in KPR-450 are prior evidence, not fresh checks performed for this specification.

## Discovery contract

Expose `discoverProviderModels(provider, { signal }) -> Promise<DiscoveredModel[]>` for the exact built-in union `"claude" | "codex" | "grok"`; a discovered row contains only `{ id, displayName }`. Providers and raw response metadata never supply operator `notes` or `addedAt`. Discovery has no database writes and never changes the provider circuit breaker, turn history, usage accounting, or assignments.

Accept the result only when SDK account metadata identifies `apiProvider: "firstParty"`, a nonempty subscription type, and a nonempty token source; reject missing/ambiguous subscription evidence. Do not log account email, organization, credentials, or raw account metadata. This intentionally leaves an API-only Claude deployment manually maintained.

Call `close()` and release the input stream in `finally`, including initialization failure, timeout, and cancellation. The installed SDK starts initialization independently of its input iterator; `supportedModels()` reads that initialization response. Use a 60-second discovery deadline that covers setup, credentials, network, and parsing; HTTP fetches also receive the caller's cancellation. The existing Grok helper has its own bounded credential-refresh requests and cannot be canceled by the scanner: let a started rotation finish safely, but discard its result after cancellation and do not fetch models or commit afterward. This child does not introduce a general pagination framework or conditional/304 cache. Error output is a constructed provider/code/status message, never a raw HTTP body, thrown SDK error, command output, URL with credentials, or token.

### Validation and failure

Normalize the entire provider result before any catalog replacement. Reject missing/wrong container types, non-object rows, blank or whitespace-padded IDs, blank display names, conflicting/duplicate normalized IDs except the explicit Claude alias case, malformed included Codex priorities, and zero usable models after filtering. Ignore unrelated vendor fields, but never silently discard a malformed eligible row and thereby manufacture removals. Reject unexpected partial/oversized responses rather than truncate. Bound raw HTTP responses to 4 MiB and the normalized replacement payload to 1 MiB; validate the complete prospective BSON commit document below MongoDB's 16 MiB limit before writing. Manual inputs pass the same normalized-payload check.

Use typed safe failure codes: `auth`, `client-version`, `http`, `timeout`, `canceled`, `malformed`, `empty`, `too-large`, and `storage`. No failure replaces models, resets `addedAt`, creates a change/history row, or advances successful discovery freshness. A storage result whose commit acknowledgment is uncertain follows the reconciliation rules below instead of being reported as a known failed discovery.

## Shared replacement and identity

The shared store accepts a manual full replacement `{ provider, models, updatedBy, changeSummary? }`, or discovered rows plus their persisted attempt token. Valid manual providers remain the three built-ins plus runtime `listPluginProviderIds()`; reject Gemini and unknown IDs in the handler. Keep the existing nonempty list rule, duplicate rejection, actor, optional summary, and diff summary response. No provider request occurs inside manual refresh.

For every accepted replacement, compare with the latest committed document under the write protocol below:

- Retained exact IDs keep `addedAt`; new IDs receive commit time. Removal followed by reintroduction is a new addition with a new timestamp.
- Manual input controls membership, names, order, and notes in full: omitted or empty notes clear a previous note, as today. Discovery controls membership, names, and order, but copies the latest notes for retained IDs. Notes of removed IDs are not archived for automatic resurrection.
- `snapshotId` is SHA-256 of UTF-8 `JSON.stringify([provider, models.map(m => [m.id, m.displayName, m.notes || null])])` over the normalized ordered rows. Dates, provenance, scan state, and summaries are excluded. Thus a name/note/order change changes snapshot identity, and an unchanged check does not. Compute this identity from legacy rows when their stored hash is absent; absence alone is not a content change.
- `revision` starts at 1 for new history-bearing writes and increases by one on every accepted manual refresh, including an identical manual refresh, and on every discovery replacement whose snapshot identity changes. `commitId` is a UUID allocated once for that logical write and retained through retries. Snapshot equality and audit-write identity are deliberately separate.
- An unchanged discovery creates no revision, history row, or notification; it only completes its successful attempt. An identical manual refresh preserves the existing audit behavior by writing a revision/history row with `+0, -0`, without a notification.
- The ID diff is set membership only; list `added` in the new order and `removed` in the previous order. A first seed of an absent/empty catalog is `bootstrap: true`, with all current IDs added. An existing nonempty legacy catalog is an existing baseline, not a bootstrap merely because it lacks new fields.

`updatedAt`, `updatedBy`, and new `source: "manual" | "discovery"` describe the latest history-bearing write; unchanged discovery leaves them unchanged. Automated writes use actor `system:model-catalog-scanner`. Keep these separate from `lastSucceededAt`, which records a successfully validated **and committed** discovery check, including an unchanged check. Manual writes never set or clear scan attempt/success fields.

## Durable storage and concurrency

Retain `agent_model_catalog` and `agent_model_catalog_versions`. Add `agent_model_catalog_changes` for small durable notice records. Use acknowledged journaled writes (`w: 1, j: true`) on these state transitions; this is compatible with the deployed standalone WiredTiger topology. No `startSession`, transactions, change streams, or replica-set prerequisite.

The catalog document remains `_id: provider` and retains its existing fields. Add optional `revision`, `commitId`, `snapshotId`, `source`, `scan`, and a **single** `pendingExport` slot. `scan` holds `{ attemptId, startedAt, leaseExpiresAt?, finishedAt?, outcome: "running" | "succeeded" | "failed", lastSucceededAt?, error?: { code, message, httpStatus? } }`; `startedAt` is the latest persisted discovery attempt, independent of `updatedAt`. An unseeded attempt can create a status-only document with no `models`. Readers still report it as unseeded.

`pendingExport` contains the complete immutable new version row plus its optional immutable change payload. New history rows retain `provider`, `snapshot`, `changeSummary`, `createdAt`, and `updatedBy`, adding `_id: commitId`, `revision`, `snapshotId`, `source`, and the ID diff/bootstrap flag. Existing legacy history rows and their ObjectIds are retained unchanged. Keep the existing `(provider, createdAt)` index; `_id` supplies idempotency for new rows.

### Replacement commit protocol

1. Recover any existing `pendingExport` for this provider. Read the current snapshot; compute the replacement, notes/`addedAt`, identity, and diff from that read. A legacy snapshot without `revision` is revision zero; use a filter requiring the field to be absent for its first update. No eager rewrite or historical notification backfill is needed.
2. Atomically compare-and-swap the catalog document using `_id`, the observed revision (or its absence), and absence of `pendingExport`. Update the complete snapshot metadata and `pendingExport` together. A discovery completion additionally requires its current running attempt token and unexpired lease, and updates success state in the same operation. A first-document insert uses unique `_id`; a duplicate-key race rereads instead of overwriting.
3. On a CAS conflict, reread, recover if necessary, and recompute against the winner, including latest notes. A scan that finishes after a manual edit may replace that edit's built-in membership under the approved next-successful-scan rule; it must preserve that edit's retained notes. A late or superseded attempt may not commit. Use a bounded conflict retry and return a retriable busy/storage error if contention persists; never an unconditional fallback write.
4. After the commit, idempotently insert the history row and, if applicable, the change row using their fixed `_id: commitId`. Duplicate-key means success only after verifying the existing immutable payload matches; otherwise report corruption and leave the envelope. Clear `pendingExport` only after both required records are confirmed durable, with a filter on that exact pending commit ID. Projection never overwrites mutable delivery fields on an existing change record.

The single-document write is the commit point. Before it, failure means no replacement. After it, the new snapshot is immediately readable and its history/change can always be reconstructed from the embedded envelope. The store returns `committed` with `recoveryPending: true` if projection fails after a known commit, and manual output explicitly says the catalog was saved with audit/change recovery pending rather than pretending nothing happened. Another replacement first retries projection; if storage remains unavailable, it fails visibly without discarding the slot. Delivery failure itself never blocks projection or another catalog write.

For an ambiguous commit acknowledgment, read by `commitId` from the catalog/pending envelope and new history to determine whether it committed; later writers cannot have removed the last evidence because they must project it first. If reconciliation cannot read Mongo, return a distinct `commit-unknown` result with the same operation ID, not a fresh automatic replacement or a recorded provider failure. Recovery is idempotent at every boundary: before history insertion, between history and change insertion, after insertion before slot clearing, and during competing recoveries. No pending export is deleted on timeout or shutdown.

Provide `recoverPendingExports(provider?)` for siblings' startup/retry passes and call provider recovery from the shared write path. Recovery catches failures per provider and reports them; it does not start its own timer. Export/read errors remain distinguishable from a provider's discovery error. Catalog reads can continue serving the last committed document with explicit recovery status.

### Attempt fencing primitives for KPR-460

Expose `replaceManual(input)`, `beginDiscoveryAttempt(provider, { attemptId, startedAt, leaseExpiresAt })`, `applyDiscovery(attempt, rows)`, `failDiscoveryAttempt(attempt, safeError, finishedAt)`, and `readCatalogState(provider)`. `begin` atomically acquires only an absent/expired scan lease and records the attempt before external work; return `busy` if another is active. Beginning an attempt preserves `lastSucceededAt` and all catalog fields, clears the previous attempt's `finishedAt`/error, and stores the new running token. KPR-460 supplies due-time decisions and a lease longer than the 60-second discovery deadline plus commit allowance. It must not hold a manual-writer lock during network work.

Completion/failure filters include the exact running token; successful commit additionally checks the lease is still valid. Superseded/expired completions return `superseded` without changing models or successful freshness. On accepted failure, retain `lastSucceededAt` and snapshot fields; record the sanitized error and completion time and release the lease. On accepted success, set `lastSucceededAt` to check completion time, clear the prior error, and release the lease. An unchanged-success update must also compare the observed catalog revision, so a racing manual replacement forces recomparison rather than incorrectly marking it as validated.

Manual operations set only catalog/audit fields, never the `scan` object. Discovery status updates set only named scan fields, never a stale copy of the full catalog. This allows manual edits during discovery and avoids losing a newer attempt or successful status. KPR-460 decides how to surface/recover an expired running attempt and when to start the next one; this child supplies the stored evidence and token guard.

Shared results have explicit discriminants: `begin` returns `started` with the persisted token or `busy`; replacement returns `committed` with `{ commitId, revision, snapshotId, bootstrap, added, removed, recoveryPending }`, `unchanged` with the existing identity and successful-check time, `superseded`, `not-committed` with a safe retriable/error code, or `commit-unknown` with its operation ID. Manual replacement cannot return `unchanged` because it always audits. Attempt-failure recording returns `recorded` or `superseded`, or reports a storage error. Siblings must not convert `committed/recoveryPending` or `commit-unknown` into a provider failure. `readCatalogState` supplies the committed snapshot, scan status, and pending-export status; `recoverPendingExports` returns per-provider recovered/pending/error results rather than rejecting all providers when one fails.

## Durable change seam for KPR-461

An immutable change payload is `{ _id: commitId, provider, revision, snapshotId, createdAt, source, updatedBy, bootstrap, added: string[], removed: string[], modelCount }`. Emit it iff bootstrap or either ID diff is nonempty. It is independent of later snapshots; never coalesce away successive changes or remove a pending change when a later scan is unchanged. Bootstrap includes all seeded IDs so its eventual summary is identifiable. The history row supplies the full associated snapshot if needed.

New outbox rows initialize `delivery: { state: "pending", attempts: 0, nextAttemptAt: createdAt }`. Expose typed collection/store access to immutable changes and a query for pending work; KPR-461 extends the separate `delivery` subdocument with recipient, claim/retry, safe diagnostic, and acknowledgment data. That sibling owns claim fencing, deduplication, acknowledgment semantics, and retry scheduling. This child does not invent a successful-dispatch interpretation, stamp a recipient, or mark anything delivered.

The contract requires KPR-461 to consume both recovered and newly committed records, retry unresolved/failed delivery without requiring a new catalog diff, and use a stable work-item identity derived from `commitId`. A delivery crash may repeat a notice; it may not silently delete one. Pending records have no TTL and are not capped by silently dropping old changes. Add a pending/due index usable by the consumer; historical catalog versions remain append-only. No notification is sent from a Mongo write callback in KPR-459.

## Acceptance and verification contract

Use Vitest with injected provider/SDK calls and a stateful Mongo test double that enforces the actual CAS filters, unique IDs, and atomic updates; no paid calls or live instance DB writes. Tests must demonstrate behavior across interleavings and crash boundaries, not merely assert that helper functions were invoked.

1. Provider fixtures verify Claude's zero-message initialization, canonical-ID/alias normalization, subscription evidence gate, and cleanup on every outcome; Codex exact host/auth/version, visibility and stable priority order including `supported_in_api: false`; Grok exact proxy host and reuse of its OAuth helper. Assert forbidden API/public fallback paths are never contacted and raw secret-bearing failures never appear in output.
2. Malformed/partial/oversized/empty results and HTTP/auth/timeout/cancellation failures preserve the previous catalog, timestamps, history, and changes. A successful unchanged check advances only scan freshness/status. No models, default IDs, or recent-launch names are hardcoded into production discovery.
3. Manual first seed, replace, identical refresh, cleared notes, plugin provider, rejected Gemini/unknown provider, duplicate/empty inputs, summary fallback, and retained/reintroduced `addedAt` behavior retain existing tool compatibility. Discovery preserves latest retained notes and overwrites built-in manual membership/names/order.
4. Concurrent manual/manual and manual/discovery writes rebase diffs and retained notes on the CAS winner. Unchanged discovery racing a manual edit rechecks. Concurrent discovery claim, expired lease takeover, and late completion cannot overwrite newer state.
5. Inject failure before/after each commit/projection boundary, restart with a fresh store, and verify one recoverable version and at most one outbox row for each committed ID change. Cover duplicate-key payload mismatch, competing recovery, ambiguous commit response, subsequent writes while export is pending, and `guardDb` refusal. Assert no transaction/session/change-stream dependency.
6. Legacy nonempty catalogs become revisioned without false bootstrap; status-only/empty catalogs seed once. Names/notes/order changes are saved and audited without alerts; multiple ID changes stay independently pending; manual plugin changes follow the same rule. Existing Gemini cache/live/error behavior and list JSON shape remain covered by existing regression tests.

Implementation must pass `npm run check`. Update tests for the shared manual writer rather than preserving the old unsafe two-write implementation in mocks. KPR-460 and KPR-461 add their lifecycle/delivery/integration coverage in their own Testing Contracts.

## Evidence, risks, and assumptions

- Repository and installed SDK examined at the KPR-450 baseline (`6abe046`); installed and lockfile SDK are `0.3.258`. Its `sdk.d.ts` declares `resolvedModel`, `accountInfo`, `supportedModels`, and `close`; `sdk.mjs` initializes before input and implements `supportedModels()` from initialization metadata. No model-generation probe was run.
- Provider endpoint entitlement evidence is recorded in the approved [epic](https://linear.app/keepur/issue/KPR-450/automatic-provider-model-catalog-scanner-3xday). The Codex [official models client source](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/endpoint/models.rs) confirms the versioned GET and `models` envelope; its [protocol source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs) confirms visibility, slug, display name, and integer priority. These are integration surfaces, not a promise that every advertised model will execute successfully.
- Non-blocking assumption: use canonical Claude `resolvedModel` where provided so an alias moving to a new model produces an ID diff; when absent, the SDK's accepted `value` is the only defensible ID. Do not infer capabilities or resolution beyond supplied metadata.
- Non-blocking assumption: missing/changed Claude subscription metadata or a missing/unparseable Codex CLI version fails discovery honestly. This may require a later provider-adapter adjustment if vendor metadata changes, but never authorizes another credential route or fabricated availability.
- Non-blocking engineering tradeoff: a failing history/outbox projection can temporarily block another catalog replacement, while the already committed catalog remains usable and recoverable. This bounded backpressure prevents unbounded catalog documents and audit loss; recipient/delivery trouble cannot cause it.
- Local Mongo configuration uses standalone WiredTiger without a replication stanza. The design consequently requires only journaled single-document atomic writes and unique `_id` indexes, not a topology change. Old out-of-process code that writes these collections unconditionally is outside the new concurrency contract; deployment must run one engine version per instance rather than overlap old/new writers.
- No blocking product question remains. The later children must consume these contracts during waterfall maturation before implementation begins.
